# Nginx 性能调优、缓存与故障排查

> 一句话结论：Nginx 调优的顺序应该是**先定位瓶颈，再调参数**；大多数“Nginx 慢”并不是 Nginx 本身，而是后端慢、连接管理不当、TLS 握手、磁盘 I/O 或内核限制。

## 1. 建立性能基线

先明确指标：

- 吞吐：RPS、带宽；
- 延迟：P50/P95/P99，区分 `$request_time` 与 `$upstream_response_time`；
- 并发连接数、活跃连接数、TIME_WAIT；
- 错误率：4xx/5xx/499；
- 资源：CPU、内存、磁盘、网络、文件描述符。

压测时分别测：

1. 直连后端；
2. 经过 Nginx 但不启用 TLS；
3. 经过 Nginx + TLS；
4. 开启缓存/压缩后。

只有对比才能判断瓶颈在 Nginx、TLS 还是后端。压测工具可选 `wrk`、`hey`、`k6`，避免用 `ab` 测长连接/HTTP2 场景。

## 2. 进程与连接数

```nginx
worker_processes auto;
worker_rlimit_nofile 100000;

events {
    worker_connections 8192;
    multi_accept on;
    use epoll;
}
```

### 2.1 最大并发怎么估

对于反向代理，一个客户端请求通常占用：

```text
1 个客户端连接 + 1 个 upstream 连接
```

因此理论并发约为：

```text
worker_processes × worker_connections / 2
```

还要扣除：

- 与后端 keepalive 池中的空闲连接；
- 健康检查、内部跳转、缓存回源；
- 长连接/WebSocket；
- 文件描述符限制。

`worker_connections` 不是越大越好。超过系统 `nofile`、内存或后端承载能力，只会把问题推后。

```bash
# 查看进程 fd 限制
cat /proc/$(pidof nginx | awk '{print $1}')/limits | grep 'open files'

# 系统级
ulimit -n
sysctl fs.file-max
```

出现 `worker_connections are not enough` 时，先确认真实并发和连接泄漏，再调整。

## 3. 静态文件与零拷贝

```nginx
http {
    sendfile on;
    tcp_nopush on;
    tcp_nodelay on;
}
```

- `sendfile on`：内核态直接发送文件，减少用户态拷贝；
- `tcp_nopush on`：配合 sendfile，把响应头和文件数据合并发送，减少小包；
- `tcp_nodelay on`：对 keepalive/小包降低延迟；
- 对大文件，`sendfile` 通常优于应用读取再写。

文件缓存：

```nginx
open_file_cache max=10000 inactive=60s;
open_file_cache_valid 30s;
open_file_cache_min_uses 2;
open_file_cache_errors on;
```

适合大量静态文件的场景。文件频繁变更时，缓存元数据可能导致短时间看到旧文件，需要根据发布方式调整 `open_file_cache_valid`。

## 4. 压缩

```nginx
gzip on;
gzip_comp_level 5;
gzip_min_length 1024;
gzip_vary on;
gzip_proxied any;
gzip_types text/plain text/css application/json application/javascript
           application/xml image/svg+xml;
```

要点：

- 不要压缩图片、视频、zip 等已压缩格式；
- `gzip_comp_level` 越高 CPU 消耗越大，5 左右通常是平衡点；
- `gzip_vary on` 让缓存正确处理 `Accept-Encoding`；
- HTTPS 下压缩敏感响应可能增加 BREACH 类攻击面，敏感页面应避免或谨慎使用；
- Brotli 需要额外模块，压缩率更好但 CPU 成本更高，按客户端支持情况启用。

## 5. 代理缓存

```nginx
proxy_cache_path /var/cache/nginx/app
                 levels=1:2
                 keys_zone=app_cache:100m
                 max_size=10g
                 inactive=60m
                 use_temp_path=off;

server {
    location /api/public/ {
        proxy_cache app_cache;
        proxy_cache_key "$scheme$request_method$host$request_uri";
        proxy_cache_valid 200 302 10m;
        proxy_cache_valid 404 1m;
        proxy_cache_lock on;
        proxy_cache_use_stale error timeout updating
                              http_500 http_502 http_503 http_504;
        add_header X-Cache-Status $upstream_cache_status always;

        proxy_pass http://app_backend;
    }
}
```

关键点：

- 只缓存明确允许缓存的响应，例如公开的商品详情、配置；
- 不要把带用户身份的响应缓存到公共 key；必要时用 Cookie/Authorization 做 bypass；
- `proxy_cache_lock` 防止缓存未命中时大量请求同时回源；
- `proxy_cache_use_stale` 在后端故障时返回旧缓存，需确认业务可接受；
- `inactive` 是“多久未被访问后淘汰”，不是响应 TTL；
- 缓存目录要有独立磁盘空间和清理策略；
- 观察 `$upstream_cache_status`：`HIT`、`MISS`、`BYPASS`、`EXPIRED`、`STALE`。

缓存 key 设计错误是常见事故：把 `Authorization` 或用户 ID 漏进 key，可能把 A 用户的数据返回给 B 用户。

## 6. 日志性能

```nginx
access_log /var/log/nginx/access.log main buffer=64k flush=5s;
```

- 缓冲日志减少磁盘写次数，但进程崩溃可能丢失少量日志；
- 高 QPS 下避免记录过多变量和请求体；
- JSON 日志便于采集，但字段越多开销越大；
- 错误日志级别不要长期开 `debug`；
- 日志轮转用 `logrotate` + `nginx -s reopen`，避免文件句柄失效；
- 采样日志适合流量分析，但错误请求应完整保留。

## 7. 内核与系统参数

在确认瓶颈后进行，不要照抄“万能优化”：

```bash
# 连接队列
sysctl net.core.somaxconn
sysctl net.ipv4.tcp_max_syn_backlog

# 本地端口范围（高并发短连接）
sysctl net.ipv4.ip_local_port_range

# TIME_WAIT 复用（需理解语义）
sysctl net.ipv4.tcp_tw_reuse
```

注意：

- `tcp_tw_recycle` 在现代内核中已移除/不推荐，不要使用；
- 调大 backlog 只能缓解，不能解决应用处理慢；
- 容器内的 sysctl 可能受宿主机限制；
- 修改前记录基线，变更后观察重传、丢包、TIME_WAIT 和延迟。

## 8. 监控端点

```nginx
location = /nginx_status {
    stub_status;
    allow 127.0.0.1;
    deny all;
}
```

输出示例：

```text
Active connections: 291
server accepts handled requests
 16630948 16630948 31070465
Reading: 6 Writing: 179 Waiting: 106
```

- `Active`：当前活跃客户端连接；
- `accepts/handled`：接受的连接数/成功处理的连接数，差距大说明资源耗尽；
- `requests`：总请求数；
- `Reading`：读取请求头的连接；
- `Writing`：处理中/发送响应；
- `Waiting`：keepalive 空闲连接。

结合 `ss -s`、`ss -lntp`、`top -H`、`pidstat` 观察连接与 CPU 分布。

## 9. 典型故障排查

### 9.1 499（客户端主动断开）

- 后端响应太慢，客户端超时；
- 客户端网络差；
- 代理层超时小于客户端超时；
- 大文件下载被中断。

看 `$request_time`、`$upstream_response_time` 和后端日志。不要只把 499 当成“客户端问题”。

### 9.2 502 Bad Gateway

常见原因：

- 后端进程未启动/端口未监听；
- 后端崩溃、连接被重置；
- 后端返回非法响应；
- upstream keepalive 与后端超时不匹配；
- 协议错误（如后端只支持 HTTP/2，Nginx 用 HTTP/1.1 转发）。

排查：

```bash
curl -v http://10.0.0.21:8080/health
ss -lntp | grep 8080
tail -f /var/log/nginx/error.log
```

错误日志中关注 `connect() failed`、`upstream prematurely closed connection`、`no live upstreams`。

### 9.3 504 Gateway Timeout

- 后端处理超过 `proxy_read_timeout`；
- 数据库慢查询、锁等待；
- 后端线程池/连接池耗尽；
- 网络丢包。

先看后端 P99 和慢日志，再决定是否调超时。**单纯调大超时会把故障时间拉长，并占用更多连接。**

### 9.4 413 Request Entity Too Large

```nginx
client_max_body_size 20m;
```

同时检查上游/应用服务器、云负载均衡的请求体限制。

### 9.5 429 Too Many Requests

检查 `limit_req`/`limit_conn` 的 zone、rate、burst 是否合理，以及是否有代理层 IP 识别错误导致所有用户共享一个限流桶。

### 9.6 连接数耗尽

错误日志出现：

```text
worker_connections are not enough
```

处理顺序：

1. 是否有连接泄漏/长连接未释放；
2. 后端是否变慢导致连接堆积；
3. `worker_connections` 与 `nofile` 是否匹配；
4. 是否需要水平扩容 Nginx；
5. 是否应对慢接口限流/熔断。

### 9.7 reload 后内存上涨

旧 worker 会等待现有连接结束才退出。长连接、WebSocket、慢请求会导致新旧 worker 并存，内存短时上升。设置合理的 `worker_shutdown_timeout`，并在发布时观察 worker 数量。

## 10. 排障命令清单

```bash
nginx -t                         # 配置语法
nginx -T                         # 完整配置
ps -ef | grep nginx
ss -lntp                         # 监听端口
ss -s                            # 连接统计
curl -I -H 'Host: example.com' http://127.0.0.1/
tail -f /var/log/nginx/error.log
```

请求链路定位：

1. DNS 是否解析到正确入口；
2. 四层负载均衡是否转发；
3. Nginx 是否收到请求（access log）；
4. upstream 地址与状态码；
5. 后端是否收到请求（后端 access log）；
6. 数据库/下游是否慢；
7. 响应是否在某一层被截断。

## 11. 调优检查表

- [ ] 是否先测量再调参？
- [ ] worker 数、连接数、fd 限制是否匹配？
- [ ] 客户端与 upstream keepalive 是否都配置正确？
- [ ] 静态文件是否使用 sendfile/缓存？
- [ ] 压缩是否只针对合适类型？
- [ ] 代理缓存 key 是否包含用户维度？
- [ ] 超时是否与后端 P99 匹配？
- [ ] 日志是否缓冲、轮转、可采集？
- [ ] 是否监控 499/502/504/429 和连接数？
- [ ] 是否做过故障注入与容量压测？

## 12. 小结

Nginx 性能调优的收益通常来自**减少不必要的拷贝、复用连接、正确缓存、合理超时和控制并发**，而不是把参数调大。排障时沿着“客户端 → 入口 → Nginx → upstream → 应用 → 数据库”逐层取证，避免在没有证据的情况下反复改配置。
