# Nginx 配置结构、location 匹配与反向代理

> 一句话结论：Nginx 配置的难点不在指令数量，而在 **上下文、继承关系、location 匹配顺序和 URI 改写**；把这四件事弄清楚，大多数“代理不生效”都能快速定位。

## 1. 配置文件的层级

```nginx
# 全局上下文
user  nginx;
worker_processes  auto;
error_log  /var/log/nginx/error.log warn;
pid        /run/nginx.pid;

events {
    worker_connections  4096;
    multi_accept on;
}

http {
    include       /etc/nginx/mime.types;
    default_type  application/octet-stream;

    log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                    '$status $body_bytes_sent "$http_referer" '
                    '"$http_user_agent" "$http_x_forwarded_for" '
                    'rt=$request_time urt=$upstream_response_time';

    access_log /var/log/nginx/access.log main;
    sendfile on;
    keepalive_timeout 65;

    include /etc/nginx/conf.d/*.conf;
}
```

常见上下文：

```text
main
├── events
└── http
    ├── upstream
    ├── map / geo / split_clients
    └── server
        ├── location
        └── if
```

规则：

- 指令只能在允许的上下文中出现；
- 子上下文通常继承父上下文，但 `location` 中的 `proxy_*`、`add_header` 等有各自的继承/覆盖规则；
- `include` 只是文本展开，不创建新作用域；
- `server` 通过 `listen` 和 `server_name` 匹配请求；
- 默认服务器用 `listen 80 default_server;` 指定。

## 2. server_name 匹配顺序

```nginx
server {
    listen 80 default_server;
    server_name _;
    return 444;
}

server {
    listen 80;
    server_name example.com www.example.com;
    # ...
}

server {
    listen 80;
    server_name ~^(?<sub>.+)\.example\.com$;
    # ...
}
```

大致优先级：

1. 精确名称；
2. 以 `*.` 开头的最长通配符；
3. 以 `.*` 结尾的最长通配符；
4. 按配置顺序的第一个正则；
5. `default_server`。

`_` 不是通配符，只是“无效名称”惯例；真正兜底要靠 `default_server`。

## 3. location 匹配顺序

```nginx
location = /health { return 200 "ok\n"; }          # 1. 精确匹配
location ^~ /static/ { ... }                        # 2. 前缀匹配且不再检查正则
location ~ \.php$ { ... }                           # 3. 区分大小写正则
location ~* \.(jpg|png|css|js)$ { ... }             # 4. 不区分大小写正则
location /api/ { ... }                              # 5. 普通前缀
location / { ... }                                  # 6. 兜底
```

匹配过程：

1. 先找精确匹配 `=`，命中立即结束；
2. 找最长前缀匹配；
3. 如果最长前缀带 `^~`，跳过正则，直接使用；
4. 否则按配置顺序检查正则，第一个命中即使用；
5. 没有正则命中时，使用最长前缀。

常见错误：

- 以为 `location /api` 能匹配 `/api` 和 `/api/xxx`，但更长的前缀 `/api/v2` 会优先；
- 正则写得太宽，抢占了静态资源；
- 在 `location` 中使用 `if` 做复杂逻辑，遇到 “if is evil” 的副作用；
- 忘记 `root`/`alias` 的路径拼接差异。

### 3.1 root 与 alias

```nginx
# 请求 /static/a.png → /data/www/static/a.png
location /static/ {
    root /data/www;
}

# 请求 /static/a.png → /data/static/a.png（location 前缀被替换）
location /static/ {
    alias /data/static/;
}
```

`alias` 通常要求 location 以 `/` 结尾、alias 也以 `/` 结尾，否则容易出现路径拼接错误。正则 location 中使用 alias 需要捕获组，复杂度较高，优先用 root 或 rewrite。

## 4. 反向代理的核心配置

```nginx
upstream app_backend {
    server 10.0.0.21:8080;
    server 10.0.0.22:8080;
    keepalive 32;
}

server {
    listen 80;
    server_name api.example.com;

    client_max_body_size 10m;

    location /api/ {
        proxy_pass http://app_backend;

        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection        "";

        proxy_connect_timeout 3s;
        proxy_send_timeout    30s;
        proxy_read_timeout    30s;

        proxy_buffering on;
        proxy_buffers 8 16k;
        proxy_buffer_size 32k;
    }
}
```

### 4.1 proxy_pass 带不带 URI 的差异

这是最容易出错的点：

```nginx
# 请求 /api/users → 转发到 http://backend/api/users
location /api/ {
    proxy_pass http://backend;
}

# 请求 /api/users → 转发到 http://backend/users
location /api/ {
    proxy_pass http://backend/;
}
```

规则简述：

- `proxy_pass` 后面没有 URI（只有主机/端口）时，原请求 URI 原样传递；
- 有 URI 时，匹配到的 location 前缀会被替换为该 URI；
- 正则 location 中使用 `proxy_pass` 不能带 URI，需要 `rewrite` 或调整 location；
- 使用变量构造 `proxy_pass` 时，URI 传递行为也会变化，务必用日志验证。

排查时在 upstream 打开访问日志，或在 Nginx 日志中记录 `$upstream_addr`、`$request_uri`，不要只看浏览器地址。

### 4.2 Host 与转发头

- `Host $host`：传递客户端请求的主机名（不含端口）；
- `Host $http_host`：包含客户端请求的端口；
- `Host $proxy_host`：传递 upstream 的主机名，很多后端不期望这个值。

后端需要识别真实客户端时，设置：

```nginx
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header X-Forwarded-Host $host;
```

安全注意：如果 Nginx 前面还有一层不可信代理，`X-Forwarded-For` 可能被伪造。应只信任已知代理链，并使用 `real_ip` 模块配置可信来源：

```nginx
set_real_ip_from 10.0.0.0/8;
real_ip_header X-Forwarded-For;
real_ip_recursive on;
```

## 5. WebSocket 与长连接

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      '';
}

server {
    location /ws/ {
        proxy_pass http://ws_backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}
```

要点：

- HTTP/1.1 才支持 Upgrade；
- `Connection` 不能固定为 `keep-alive`，需要根据 `Upgrade` 动态设置；
- 长连接会占用 worker 连接数，需评估容量；
- 代理层/云负载均衡的空闲超时要大于业务心跳间隔；
- WebSocket 连接不能像普通 HTTP 一样被 upstream keepalive 池复用。

## 6. 请求体、超时与缓冲

```nginx
client_max_body_size 20m;          # 默认 1m，超出返回 413
client_body_timeout 30s;
client_header_timeout 10s;
send_timeout 30s;

proxy_connect_timeout 3s;          # 与后端建立连接
proxy_send_timeout 30s;            # 向后端发送请求
proxy_read_timeout 30s;            # 等待后端响应
```

常见误区：

- 只调大 `proxy_read_timeout`，但后端本身已经超时；
- 上传大文件时只改 `client_max_body_size`，没有考虑磁盘缓冲和超时；
- 开启 `proxy_request_buffering off` 后，后端要能处理慢客户端；
- 响应很大时关闭 `proxy_buffering`，会占用更多连接时间，但能降低首字节延迟。

超时值应来自业务 SLA 和后端实际 P99，而不是随意设为 60s、300s。

## 7. 静态资源与 SPA

```nginx
server {
    listen 80;
    server_name www.example.com;
    root /var/www/site;
    index index.html;

    location /assets/ {
        expires 30d;
        add_header Cache-Control "public, immutable";
        try_files $uri =404;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

注意：

- `try_files` 最后一项可以是 URI 或 `=404`；
- SPA 的 `index.html` 不应长期缓存，否则发布后用户看到旧版本；
- 带 hash 的静态资源可长缓存，文件名变化即可失效；
- 开启 `gzip`/`brotli` 时注意已经压缩的图片、视频无需重复压缩。

## 8. 日志与调试

```nginx
log_format detailed '$remote_addr "$request" $status '
                    'rt=$request_time '
                    'ua=$upstream_addr '
                    'urt=$upstream_response_time '
                    'host=$host uri=$request_uri';

access_log /var/log/nginx/access.log detailed;
error_log  /var/log/nginx/error.log warn;
```

字段含义：

- `$request_time`：从读到客户端第一个字节到发送完响应的总时间；
- `$upstream_response_time`：Nginx 等待后端响应的时间，可能包含多个 upstream（重试）；
- `$upstream_addr`：实际访问的后端地址；
- `$upstream_status`：后端返回状态码。

常用命令：

```bash
nginx -t                 # 检查配置语法
nginx -T                 # 打印完整生效配置
nginx -s reload          # 平滑重载
nginx -s reopen          # 重新打开日志文件
```

`reload` 会启动新 worker、优雅关闭旧 worker；如果旧 worker 上有长连接，退出会持续到连接结束。变更前先 `nginx -t`，变更后观察错误日志和 5xx。

## 9. 常见错误与定位

| 现象 | 常见原因 | 排查 |
| --- | --- | --- |
| 404 | root/alias 路径错误、location 不匹配 | `nginx -T`、访问日志、`try_files` |
| 403 | 权限不足、目录索引关闭 | 文件权限、SELinux、`autoindex` |
| 413 | 请求体超过限制 | `client_max_body_size` |
| 502 | 后端拒绝连接/进程崩溃/协议错误 | `error.log`、`upstream_addr`、后端健康 |
| 504 | 后端处理超时 | `proxy_read_timeout`、后端 P99、数据库慢查询 |
| 499 | 客户端提前断开 | 客户端超时、后端太慢、网络 |
| 循环重定向 | `X-Forwarded-Proto` 未传、后端强制 HTTPS | 转发头、后端配置 |

502 与 504 的区分很重要：502 通常是“连上了但响应非法/连接被重置”，504 是“等待超时”。不要只靠调大超时解决 502。

## 10. 小结

Nginx 配置的关键是：**请求如何匹配 server/location → URI 如何被改写 → 转发哪些头 → 超时和缓冲如何影响行为**。遇到代理问题时，先 `nginx -T` 看最终配置，再用访问日志中的 `$upstream_*` 变量确认请求到底去了哪里。
