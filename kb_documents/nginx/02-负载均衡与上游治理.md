# Nginx 负载均衡、健康检查与上游治理

> 一句话结论：负载均衡不仅是“把请求分给多台机器”，还要处理**健康判断、连接复用、失败重试、会话保持和发布流量**；其中重试策略直接关系到请求是否会被重复执行。

## 1. upstream 基础

```nginx
upstream app_backend {
    zone app_backend 64k;
    least_conn;

    server 10.0.0.21:8080 weight=3 max_fails=3 fail_timeout=10s;
    server 10.0.0.22:8080 weight=1 max_fails=3 fail_timeout=10s;
    server 10.0.0.23:8080 backup;

    keepalive 64;
    keepalive_requests 1000;
    keepalive_timeout 60s;
}
```

- `zone`：共享内存，保存上游节点的状态；多 worker 下建议配置；
- `weight`：权重，默认 1；
- `max_fails` / `fail_timeout`：被动健康检查参数，在 `fail_timeout` 内失败 `max_fails` 次后，节点在接下来的 `fail_timeout` 内被标记为不可用；
- `backup`：备用节点，主节点不可用时才使用；
- `down`：手动摘除节点；
- `keepalive`：每个 worker 保留的空闲长连接数，不是“最大连接数”。

## 2. 负载均衡算法

### 2.1 轮询（默认）

```nginx
upstream backend {
    server 10.0.0.21:8080;
    server 10.0.0.22:8080;
}
```

按请求依次分发，配合 `weight` 实现加权轮询。适合后端处理能力相近、请求耗时均匀的场景。

### 2.2 最少连接

```nginx
upstream backend {
    least_conn;
    server 10.0.0.21:8080;
    server 10.0.0.22:8080;
}
```

优先发给当前活跃连接数最少的节点，适合请求耗时差异大、长连接较多的场景。它看的是“连接数”，不是“CPU 使用率”或“响应时间”。

### 2.3 IP 哈希

```nginx
upstream backend {
    ip_hash;
    server 10.0.0.21:8080;
    server 10.0.0.22:8080;
}
```

同一客户端 IP 固定到同一后端，适合简单的会话保持。但在 NAT、代理、移动网络下大量用户共享出口 IP，容易造成倾斜；节点增减也会导致重新分布。

### 2.4 一致性哈希

```nginx
upstream cache_backend {
    hash $request_uri consistent;
    server 10.0.0.31:8080;
    server 10.0.0.32:8080;
    server 10.0.0.33:8080;
}
```

`consistent` 使用一致性哈希环，节点增减时只影响部分 key，适合缓存分片。`hash` 的 key 可以是 `$request_uri`、`$cookie_session`、`$arg_id` 等，但要注意分布均匀性。

### 2.5 随机与二选一

```nginx
upstream backend {
    random two least_conn;
    server 10.0.0.21:8080;
    server 10.0.0.22:8080;
    server 10.0.0.23:8080;
}
```

随机选择，`two least_conn` 表示随机选两个再取连接数较少的，兼顾分布与负载。适合大规模后端，能避免所有节点同步争抢。

### 2.6 算法选择速查

| 场景 | 推荐 |
| --- | --- |
| 后端同质、请求短 | 轮询/加权轮询 |
| 请求耗时差异大 | `least_conn` |
| 简单会话保持 | `ip_hash`（注意 NAT） |
| 缓存分片 | `hash $key consistent` |
| 大规模无状态服务 | `random two least_conn` |
| 灰度/蓝绿 | 权重 + 独立 upstream 或 `split_clients` |

## 3. 被动健康检查的边界

开源版 Nginx 主要依赖**被动健康检查**：

```nginx
upstream backend {
    server 10.0.0.21:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.22:8080 max_fails=3 fail_timeout=10s;
}
```

含义：在 `fail_timeout` 时间窗口内失败达到 `max_fails` 次，节点被摘除 `fail_timeout` 时间，之后会再尝试。

局限：

- 没有请求时不会主动探测，无法提前发现故障；
- “失败”的判定依赖 `proxy_next_upstream` 配置；
- 节点恢复后要等下一次尝试才重新纳入；
- 无法区分“端口活着但业务不可用”；
- 开源版没有 `health_check` 主动检查指令（NGINX Plus 或第三方模块才有）。

实践建议：

- 应用提供 `/healthz`（进程存活）和 `/readyz`（可接流量）两个端点；
- 用外部健康检查器/服务发现/负载均衡器做主动探测；
- Nginx 的被动检查作为最后一道兜底；
- 健康检查不要级联检查所有下游，否则一个依赖故障会把全部节点摘除。

## 4. 重试：最容易埋坑的地方

```nginx
location /api/ {
    proxy_pass http://backend;

    proxy_next_upstream error timeout http_502 http_503 http_504;
    proxy_next_upstream_tries 2;
    proxy_next_upstream_timeout 5s;
}
```

默认只对 `error` 和 `timeout` 重试，且默认不会重试非幂等请求。显式加入 `http_502` 等状态码后，要特别小心：

- **POST 创建订单**：后端可能已经执行成功，只是响应阶段连接断开；重试会造成重复下单；
- **支付/扣款**：绝不能盲目重试；
- **文件上传**：请求体可能已被后端部分处理。

如果确实需要重试非幂等请求，必须满足以下之一：

1. 业务接口支持幂等键（`Idempotency-Key`），后端去重；
2. 后端明确返回“未执行”；
3. 重试由应用层根据业务状态决定，而不是代理层无脑重放。

`proxy_next_upstream non_idempotent;` 会允许重试非幂等请求，风险极高，除非有幂等保障，否则不要开启。

还需要注意：

- `proxy_next_upstream_tries` 限制总尝试次数，避免放大流量；
- `proxy_next_upstream_timeout` 限制总重试时间；
- 重试会消耗后端连接和后端容量，故障时可能形成“重试风暴”；
- 对 5xx 的自动重试可能掩盖真实故障，必须配合监控。

## 5. upstream keepalive：减少握手开销

```nginx
upstream backend {
    server 10.0.0.21:8080;
    server 10.0.0.22:8080;
    keepalive 64;
}

location / {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
}
```

要点：

- 必须使用 HTTP/1.1，并清除 `Connection: close`，否则连接无法复用；
- `keepalive` 是每个 worker 的空闲连接池大小，不是全局上限；
- `keepalive_requests` 控制单连接最大请求数，避免连接过老；
- 后端也要配置合理的 keepalive 超时，否则 Nginx 复用时后端已关闭；
- 连接池只对没有 `Upgrade` 的普通 HTTP 请求有效；
- 后端返回 `Connection: close` 时，连接不会进入池。

如果使用 WebSocket，需按 Upgrade 场景单独配置，不能与普通 keepalive 混用同一套 `Connection` 头。

## 6. 上游 TLS

```nginx
upstream secure_backend {
    server 10.0.0.31:8443;
    keepalive 16;
}

location / {
    proxy_pass https://secure_backend;

    proxy_http_version 1.1;
    proxy_set_header Connection "";

    proxy_ssl_server_name on;
    proxy_ssl_name api.internal.example.com;
    proxy_ssl_verify on;
    proxy_ssl_trusted_certificate /etc/nginx/certs/internal-ca.pem;
    proxy_ssl_session_reuse on;
}
```

- `proxy_ssl_server_name on` 发送 SNI；
- `proxy_ssl_name` 指定校验的主机名；
- 生产环境应开启 `proxy_ssl_verify`，不要关闭证书校验；
- 上游使用自签 CA 时，提供正确的信任链；
- TLS 握手有成本，连接复用与会话复用能降低开销。

## 7. 动态上游与服务发现

传统 `upstream` 里的 IP 是静态的。容器/云环境中后端 IP 经常变化，常见方案：

1. **服务发现 + 模板渲染**：Consul Template、confd 监听变更，生成 upstream 配置并 `nginx -s reload`；
2. **DNS + `resolve`**：较新版本支持在 upstream 中使用 `resolve` 动态解析，需要配合 `resolver` 和共享内存 `zone`；旧版本通常在启动时解析一次，DNS 变化需 reload；
3. **Kubernetes Ingress Controller**：由控制器监听 Service/EndpointSlice，动态生成配置；
4. **服务网格/API 网关**：把负载均衡和服务发现下沉到专用组件。

无论哪种方式，都要处理：

- 配置变更的原子性与校验（先 `nginx -t`）；
- reload 频率过高导致的 worker 抖动；
- DNS TTL 与解析失败；
- 新节点未就绪就被加入；
- 摘除节点时的连接排空。

## 8. 灰度、蓝绿与流量切分

### 8.1 按权重

```nginx
upstream app {
    server 10.0.0.21:8080 weight=9;  # 稳定版
    server 10.0.0.31:8080 weight=1;  # 灰度版
}
```

简单，但粒度较粗，且需要 reload 才能改权重。

### 8.2 按比例分流

```nginx
split_clients "${remote_addr}${http_user_agent}" $variant {
    10%     canary;
    *       stable;
}

map $variant $backend_addr {
    canary  10.0.0.31:8080;
    default 10.0.0.21:8080;
}

location / {
    # 变量模式下显式拼接原始 URI，避免路径/查询串行为不符合预期
    proxy_pass http://$backend_addr$request_uri;
}
```

注意：`proxy_pass` 使用变量时，URI 传递和 upstream 解析行为会变化，必须用日志验证；变量值使用域名时还需要 `resolver`。同时要保证分流键稳定，避免同一用户频繁切换版本。更复杂的按比例路由，建议交给 Ingress Controller、服务网格或 API 网关。

### 8.3 按 Header/Cookie

```nginx
map $http_x_canary $backend_pool {
    "true"  canary;
    default stable;
}
```

适合内部测试、特定用户灰度。不要把可伪造的 Header 当作安全边界。

## 9. 监控与排障

```nginx
log_format upstream_log '$remote_addr "$request" $status '
                        'upstream=$upstream_addr '
                        'ustatus=$upstream_status '
                        'urt=$upstream_response_time '
                        'rt=$request_time';
```

关注：

- 各 upstream 的请求量、5xx 比例、P99；
- `$upstream_connect_time`、`$upstream_header_time`、`$upstream_response_time`；
- 重试次数与 `proxy_next_upstream` 触发原因；
- 连接池命中、TIME_WAIT、后端 keepalive 状态；
- 节点摘除/恢复事件；
- 发布期间的流量分布。

常见问题：

| 现象 | 可能原因 |
| --- | --- |
| 流量严重倾斜 | 权重配置、`ip_hash` 的 NAT、会话粘性、DNS 缓存 |
| 间歇性 502 | 某节点异常、keepalive 与后端超时不匹配、协议错误 |
| 发布时大量 502 | 新节点未就绪、摘除太快、连接未排空 |
| 重试导致重复订单 | 对非幂等请求开启重试 |
| 后端连接数暴涨 | 未启用 keepalive、`Connection` 头未清理、短连接 |

## 10. 小结

负载均衡的目标不是“平均”，而是**在故障和发布过程中仍然把请求送到健康、可用的后端**。请优先保证：健康检查能反映真实可用性、重试不会破坏幂等性、keepalive 两端匹配、流量切换可观测。权重和算法只是最后一层。
