# Kubernetes 故障排查与生产运维手册

> 一句话结论：排障要沿“控制面 → 节点 → 工作负载 → Service/DNS → Ingress → 应用/依赖”逐层缩小范围；生产运维则要把**备份、升级、容量、安全、可观测性**做成常态，而不是事故时临时发挥。

## 1. 分层排障模型

```text
集群/控制面
  └─ 节点
       └─ Pod/容器
            └─ Service/EndpointSlice
                 └─ DNS/NetworkPolicy
                      └─ Ingress/负载均衡
                           └─ 应用与外部依赖
```

每层先问三个问题：

1. 这一层的“期望状态”是什么？
2. 实际状态是什么？
3. 哪个控制器/组件负责调谐，它为什么没有动作？

## 2. 第一轮信息采集

```bash
kubectl cluster-info
kubectl get nodes -o wide
kubectl get pods -A -o wide | head -50
kubectl get events -A --sort-by=.lastTimestamp | tail -50
kubectl get --raw='/readyz?verbose'
kubectl get --raw='/livez?verbose'
```

重点：

- 节点是否 `Ready`；
- 是否有大量 Pod 异常集中在某节点/某命名空间；
- Events 中的 `FailedScheduling`、`FailedMount`、`Unhealthy`、`BackOff`；
- apiserver `/readyz` 是否通过；
- 最近是否有发布、扩缩容、节点维护、证书到期。

## 3. Pod 异常状态

### 3.1 Pending

表示尚未完成调度或前置条件不满足。

```bash
kubectl describe pod <pod> -n <ns>
kubectl get events -n <ns> --field-selector involvedObject.name=<pod>
```

常见原因：

| 事件 | 原因 |
| --- | --- |
| `Insufficient cpu/memory` | requests 过大或节点资源不足 |
| `node(s) had untolerated taint` | 污点/容忍不匹配 |
| `didn't match node selector/affinity` | 标签或亲和性错误 |
| `unbound immediate PersistentVolumeClaims` | PVC 未绑定 |
| `volume node affinity conflict` | PV 与节点拓扑不匹配 |
| `exceeded quota` | 命名空间配额不足 |
| `no nodes available` | 集群无可用节点/全部 cordon |

处理：调整 requests、扩容节点、修正标签/污点、修复 PVC/StorageClass，而不是盲目删除 Pod。

### 3.2 ImagePullBackOff / ErrImagePull

```bash
kubectl describe pod <pod> -n <ns> | sed -n '/Events/,$p'
```

检查：

- 镜像名、tag 是否存在（避免 `latest` 漂移）；
- 私有仓库的 `imagePullSecrets`；
- 节点到仓库的网络/DNS/证书；
- 仓库限流；
- 节点磁盘空间；
- 架构不匹配（amd64 镜像跑在 arm64 节点）。

### 3.3 CrashLoopBackOff

容器启动后反复退出，kubelet 指数退避重启（最长约 5 分钟）。

```bash
kubectl logs <pod> -n <ns> --previous
kubectl logs <pod> -n <ns> --all-containers=true
kubectl describe pod <pod> -n <ns>
```

看退出码：

| 退出码 | 常见含义 |
| --- | --- |
| `0` | 正常退出，但长期服务不应退出；检查启动命令 |
| `1` | 应用错误/未捕获异常 |
| `126` | 命令不可执行/权限不足 |
| `127` | 命令不存在 |
| `137` | 收到 SIGKILL，常见于 OOMKilled 或强制终止 |
| `143` | 收到 SIGTERM，优雅终止 |

常见原因：

- 配置/环境变量缺失；
- 依赖服务不可达；
- 启动命令/参数错误；
- 权限/文件系统只读；
- 探针配置导致被杀；
- 内存 limit 过低；
- 迁移/初始化失败。

### 3.4 OOMKilled

```bash
kubectl describe pod <pod> -n <ns> | grep -A5 'Last State'
```

- 容器内存超过 limit，被内核 OOM Killer 杀死；
- Java/Go 等运行时要注意堆上限与容器 limit 的关系；
- 节点内存压力也可能驱逐 Pod，但不一定标记 OOMKilled；
- 解决不是简单调大 limit：先看内存曲线、泄漏、缓存、并发。

### 3.5 Evicted

节点资源压力（内存、磁盘、PID）时，kubelet 会驱逐 Pod。

```bash
kubectl get pod <pod> -n <ns> -o yaml | grep -A10 status
kubectl describe node <node> | grep -A10 Conditions
```

检查节点 `MemoryPressure`、`DiskPressure`、`PIDPressure`，以及 Pod 的 ephemeral-storage 使用。清理镜像/日志/临时文件，或迁移负载。

### 3.6 Terminating 卡住

常见原因：

- finalizer 未完成；
- 节点 NotReady，kubelet 无法确认容器已停止；
- 卷卸载/挂载失败；
- apiserver 不可达；
- 优雅终止时间未到。

```bash
kubectl get pod <pod> -n <ns> -o yaml | grep -A5 finalizers
kubectl describe pod <pod> -n <ns>
```

不要直接删除 finalizer，除非确认外部资源已清理；否则可能留下孤儿云资源/卷。

## 4. 节点 NotReady

在节点上检查：

```bash
systemctl status kubelet
journalctl -u kubelet -n 200 --no-pager
systemctl status containerd
crictl ps
df -h
free -m
dmesg -T | tail -50
```

常见原因：

- kubelet 未运行/配置错误；
- 容器运行时异常；
- 磁盘满、inode 耗尽；
- 内存压力；
- 网络插件未就绪；
- 证书过期；
- 节点与 apiserver 网络不通；
- 云厂商节点生命周期操作。

控制面查看：

```bash
kubectl describe node <node>
kubectl get node <node> -o yaml | grep -A20 conditions
```

维护：

```bash
kubectl cordon <node>
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data
# 维护完成后
kubectl uncordon <node>
```

`drain` 会受 PDB 约束；如果一直阻塞，检查 PDB、DaemonSet、本地存储和 finalizer。

## 5. Service 与 DNS

### 5.1 Service 没有 Endpoint

```bash
kubectl get svc <svc> -n <ns> -o wide
kubectl get endpointslices -n <ns> -l kubernetes.io/service-name=<svc>
kubectl get pods -n <ns> --show-labels
kubectl describe pod <pod> -n <ns>
```

检查 selector、Pod readiness、端口名、协议。Endpoints 为空时，先修 Pod/标签，不要先怀疑 kube-proxy。

### 5.2 DNS 解析失败

```bash
# 使用集群内可拉取的调试镜像，示例为 busybox；离线环境替换为内部镜像
kubectl run -it --rm dns-test --image=busybox:1.36 --restart=Never -- \
  /bin/sh -c 'nslookup kubernetes.default.svc.cluster.local'
```

检查：

- CoreDNS Pod 是否运行；
- CoreDNS 日志与 ConfigMap；
- Pod 的 `/etc/resolv.conf`；
- NetworkPolicy 是否允许 UDP/TCP 53；
- 是否使用了错误的命名空间/短域名；
- 节点本地 DNS 缓存/上游 DNS 故障。

Kubernetes DNS 名称：

```text
<service>.<namespace>.svc.cluster.local
<pod-name>.<headless-service>.<namespace>.svc.cluster.local
<pod-ip-with-dashes>.<namespace>.pod.cluster.local
```

例如 Pod IP `10.244.1.7` 对应 `10-244-1-7.default.pod.cluster.local`。

### 5.3 连接超时/拒绝

- Service 端口与 targetPort 不一致；
- 应用监听 `127.0.0.1` 而不是 `0.0.0.0`；
- NetworkPolicy/安全组阻断；
- CNI/MTU 问题；
- kube-proxy/iptables/IPVS 异常；
- 后端 Pod 已终止但仍有连接。

## 6. Ingress 与入口

```bash
kubectl get ingress -n <ns>
kubectl describe ingress <ingress> -n <ns>
kubectl get svc,endpointslice -n <ns>
kubectl logs -n ingress-nginx deploy/ingress-nginx-controller --tail=200
```

- `ADDRESS` 为空：控制器/LoadBalancer 未就绪；
- 404：host/path 不匹配，或控制器未选中该 Ingress；
- 502：后端连接失败、端口错误、Pod 未 Ready；
- 504：后端处理超时；
- TLS 错误：Secret 缺失、证书域名不匹配、证书链不完整。

先用 `kubectl port-forward` 绕过入口验证 Service，再检查 Ingress Controller。

## 7. 控制面与 etcd

### 7.1 健康检查

```bash
kubectl get --raw='/readyz?verbose'
kubectl get --raw='/livez?verbose'
kubectl get pods -n kube-system
```

自建集群的 etcd：

```bash
ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  endpoint health

ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  endpoint status --write-out=table
```

关注：

- 成员是否健康、是否有 leader；
- DB size、raft index、leader 变更；
- 磁盘 fsync 延迟（etcd 对磁盘延迟非常敏感）；
- `NOSPACE`/`CORRUPT` 告警；
- 证书有效期。

### 7.2 备份

```bash
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-$(date +%F-%H%M).db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

ETCDCTL_API=3 etcdctl snapshot status /backup/etcd-2026-11-11-0200.db --write-out=table
```

备份还应包括：

- 集群证书与 CA；
- Secrets 加密配置及密钥（否则恢复后 Secret 无法解密）；
- 集群清单/GitOps 仓库；
- PV 数据/快照；
- 云资源、负载均衡、DNS 配置。

etcd 快照不是应用数据备份。数据库、对象存储等要有各自的备份策略。

### 7.3 恢复

etcd 恢复是**集群级操作**，必须停止所有 etcd 成员，使用相同的初始集群配置恢复，避免脑裂。典型流程：

```bash
# 在每个成员上恢复到新的 data-dir（示例，需按实际拓扑调整）
etcdctl snapshot restore /backup/etcd.db \
  --name etcd-1 \
  --initial-cluster etcd-1=https://10.0.0.11:2380,etcd-2=https://10.0.0.12:2380,etcd-3=https://10.0.0.13:2380 \
  --initial-advertise-peer-urls https://10.0.0.11:2380 \
  --data-dir /var/lib/etcd-restore
```

恢复后：

- 校验 apiserver、controller-manager、scheduler 是否正常；
- 校验关键对象与 Secret；
- 检查证书、Token、云资源；
- 做应用连通性验证；
- 记录实际 RTO。

托管 Kubernetes 通常不暴露 etcd，备份策略应使用厂商提供的控制面备份/集群快照能力。

### 7.4 碎片与告警

- etcd 的 `NOSPACE` 告警通常需要 compaction + defrag；
- defrag 会阻塞成员，逐个执行，避免同时进行；
- 控制 DB 大小，定期 compaction；
- 监控磁盘 IOPS/fsync 延迟，etcd 不适合与高 IO 工作负载共享磁盘；
- 不要随意删除 etcd 数据目录。

## 8. 升级与变更

### 8.1 版本策略

- 遵循官方版本偏差策略：`kubectl` 通常只支持与 apiserver 相差一个 minor；kubelet 不应新于 apiserver，允许落后若干 minor；
- 一次只升一个 minor，不要跨多个版本；
- 先看 release notes、弃用 API、行为变更；
- 在预发集群演练，记录回滚路径。

```bash
kubectl version --output=yaml
kubectl api-resources
kubectl get --raw='/metrics' | head
```

检查弃用 API 可用 `pluto`、`kubent` 等工具，或查看 apiserver 审计日志中的 deprecated 警告。

### 8.2 升级顺序

自建集群的常见顺序：

1. etcd（按成员滚动，保持 quorum）；
2. 控制面（apiserver/controller-manager/scheduler，逐个）；
3. 节点（cordon → drain → 升级 kubelet/kube-proxy/运行时 → uncordon）；
4. 工作负载与 CRD/Operator；
5. 验证。

注意：

- 不要同时升级所有控制面成员；
- 不要同时 drain 多个可用区的节点；
- 先升级一个节点做金丝雀；
- 确保 PDB、容量和回滚镜像可用；
- 升级后检查 CoreDNS、CNI、CSI、Ingress Controller 的兼容性。

## 9. 生产运维体系

### 9.1 备份与灾难恢复

- etcd 快照 + 证书 + 加密配置；
- PV 快照/应用级备份（Velero 等）；
- GitOps 仓库保存清单；
- 定期恢复演练，验证 RTO/RPO；
- 多可用区/多集群容灾方案与 DNS/流量切换。

### 9.2 可观测性

- **Metrics**：Prometheus + kube-state-metrics + node-exporter + 应用指标；
- **Logs**：容器日志采集、集中存储、保留策略；
- **Traces**：OpenTelemetry/Jaeger；
- **Events**：Kubernetes Event 不是长期审计日志，需单独采集；
- **SLO**：错误率、延迟、饱和度、可用性；
- 告警关注用户可见症状，而不是每个 Pod 重启都报警。

### 9.3 安全

- RBAC 最小权限，避免共享 cluster-admin；
- Pod Security Standards（baseline/restricted）；
- NetworkPolicy 默认拒绝，按需放行；
- 镜像扫描、签名、准入控制；
- Secret 加密、外部密钥管理、轮换；
- 审计日志；
- 供应链安全（SBOM、可信镜像仓库）；
- 节点基线加固与自动补丁。

### 9.4 容量与成本

- requests/limits 定期校准；
- 节点池按工作负载类型划分；
- HPA/Cluster Autoscaler 有上限与告警；
- 识别长期低利用率命名空间/服务；
- 使用成本分配标签；
- 避免为了“看起来稳定”无限超配。

## 10. 常见故障速查表

| 现象 | 优先检查 |
| --- | --- |
| Pod Pending | 资源、污点、亲和性、PVC、配额 |
| ImagePullBackOff | 镜像名、仓库认证、网络、架构 |
| CrashLoopBackOff | 日志、退出码、配置、依赖、探针 |
| OOMKilled | 内存 limit、堆配置、泄漏、节点压力 |
| Service 无 Endpoint | selector、readiness、端口 |
| DNS 失败 | CoreDNS、NetworkPolicy、resolv.conf |
| Ingress 502 | Service/端口/Endpoint、控制器日志 |
| Node NotReady | kubelet、运行时、磁盘、网络、证书 |
| etcd 慢/告警 | 磁盘 fsync、DB 大小、quorum、defrag |
| 升级后 API 报错 | 弃用 API、CRD/Operator 兼容性 |

## 11. 小结

Kubernetes 排障的关键是分层和证据：先看对象状态与 Events，再看日志与指标，最后进入节点/控制面。生产运维则要把备份、升级、容量、安全和可观测性做成可演练的流程。**能恢复、能回滚、能观测**，比“集群看起来正常”更重要。
