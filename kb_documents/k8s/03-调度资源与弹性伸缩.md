# Kubernetes 调度、资源管理与弹性伸缩

> 一句话结论：调度看 **requests**，运行时限看 **limits**，扩容看 **指标与 requests 的比值**；三者配置不一致，就会出现“节点明明有空闲却调度不上”“Pod 没超限却被 OOMKilled”“HPA 不扩容”等典型问题。

## 1. requests 与 limits

```yaml
resources:
  requests:
    cpu: 500m
    memory: 512Mi
  limits:
    cpu: "1"
    memory: 1Gi
```

- **requests**：调度器预留的资源，也是 HPA 利用率计算的分母；
- **limits**：容器运行时强制的上限；
- CPU 超限会被节流（throttling），表现为延迟升高；
- 内存超限会触发 OOMKilled，容器退出并按重启策略重启；
- 节点资源不足时，kubelet 按 QoS/优先级驱逐 Pod。

### 1.1 CPU 与内存的差异

| 资源 | 单位 | 超限行为 | 可压缩 |
| --- | --- | --- | --- |
| CPU | 核，`100m` = 0.1 核 | CFS 节流，变慢 | 是 |
| 内存 | 字节，`Mi/Gi` | OOMKilled | 否 |

CPU 是“时间片”，内存是“不可压缩资源”。因此内存 requests/limits 要比 CPU 更谨慎。

### 1.2 常见配置错误

- 只设 limits 不设 requests：调度器按 0 预留，节点超卖，容易互相挤压；
- requests 远低于实际：HPA 以为用量很高，过早扩容；节点过度装箱；
- limits 远高于 requests：突发时争抢，稳定性下降；
- 内存 limit 太低：频繁 OOMKilled；
- CPU limit 太低：应用延迟抖动，GC/线程池受影响；
- 所有容器都设成相同值，不区分核心服务与旁路组件。

建议从压测和监控的 P95/P99 用量出发，先设 requests，再设合理 burst 的 limits；对延迟敏感服务可考虑不设 CPU limit（依赖 requests 和节点隔离），但要评估风险。

## 2. QoS 等级

| QoS | 条件 | 驱逐优先级 |
| --- | --- | --- |
| `Guaranteed` | 每个容器都设置 CPU/内存 requests 且等于 limits | 最后被驱逐 |
| `Burstable` | 至少一个容器设置 requests/limits，但不满足 Guaranteed | 中间 |
| `BestEffort` | 所有容器都没有 requests/limits | 最先被驱逐 |

```bash
kubectl get pod <pod> -o jsonpath='{.status.qosClass}{"\n"}'
```

Guaranteed 并不等于“绝对不会被驱逐”：节点压力、优先级抢占、维护仍可能影响。它只是相对更受保护。

## 3. 调度器如何选择节点

简化流程：

```text
1. 过滤（Filter）：资源、节点选择器、污点、亲和性、卷、拓扑等
2. 打分（Score）：资源均衡、镜像本地性、拓扑分布等
3. 绑定（Bind）：写入 Pod 的 nodeName
```

### 3.1 nodeSelector 与 nodeAffinity

```yaml
spec:
  nodeSelector:
    disktype: ssd
```

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values: ["zone-a", "zone-b"]
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80
          preference:
            matchExpressions:
              - key: node-type
                operator: In
                values: ["memory-optimized"]
```

- `required` 不满足则 Pending；
- `preferred` 只是加分，不保证；
- `IgnoredDuringExecution` 表示调度后节点标签变化不会驱逐 Pod；
- 标签键值必须与节点实际标签一致，拼写错误会导致无法调度。

### 3.2 污点与容忍

```bash
kubectl taint nodes node-1 dedicated=ml:NoSchedule
```

```yaml
spec:
  tolerations:
    - key: dedicated
      operator: Equal
      value: ml
      effect: NoSchedule
```

效果：

- `NoSchedule`：新 Pod 不调度，已有 Pod 保留；
- `PreferNoSchedule`：尽量不调度；
- `NoExecute`：驱逐不容忍的已有 Pod。

容忍只是“允许”调度到有污点的节点，不代表“只调度到那里”；通常还要配合 nodeAffinity/nodeSelector。

### 3.3 Pod 亲和与反亲和

```yaml
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels:
              app.kubernetes.io/name: web
          topologyKey: kubernetes.io/hostname
```

- `podAffinity`：希望与某些 Pod 靠近（同节点/同可用区）；
- `podAntiAffinity`：希望远离；
- `topologyKey` 决定“拓扑域”，如 `kubernetes.io/hostname`、`topology.kubernetes.io/zone`；
- `required` 反亲和在大规模副本时可能无法满足，导致 Pending；高副本场景优先用 `topologySpreadConstraints`。

### 3.4 拓扑分布

```yaml
spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule
      labelSelector:
        matchLabels:
          app.kubernetes.io/name: web
```

让 Pod 在可用区/节点间尽量均匀。`maxSkew` 是允许的最大偏斜；`whenUnsatisfiable` 可选 `DoNotSchedule` 或 `ScheduleAnyway`。跨可用区部署还要考虑存储、网络延迟和流量成本。

## 4. 资源配额与默认值

### 4.1 ResourceQuota

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: prod-quota
  namespace: prod
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    pods: "100"
```

```bash
kubectl describe resourcequota -n prod
```

配额是命名空间级的总量限制。配额耗尽时，新 Pod 可能无法创建，Event 中会提示 `exceeded quota`。

### 4.2 LimitRange

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: prod
spec:
  limits:
    - type: Container
      default:
        cpu: 500m
        memory: 512Mi
      defaultRequest:
        cpu: 100m
        memory: 128Mi
      max:
        cpu: "2"
        memory: 2Gi
```

`LimitRange` 可提供默认 requests/limits，并限制单容器最大/最小值。默认值不能替代容量规划，否则所有服务都被套上相同配置。

## 5. HPA：水平扩缩容

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
  namespace: prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30
      policies:
        - type: Percent
          value: 100
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Pods
          value: 1
          periodSeconds: 60
```

### 5.1 HPA 的计算逻辑

CPU 利用率基于 **requests**：

```text
利用率 = 实际 CPU 使用量 / requests.cpu
期望副本数 ≈ ceil(当前副本数 × 当前利用率 / 目标利用率)
```

因此：

- requests 设得太低，利用率虚高，HPA 过早扩容；
- requests 设得太高，利用率偏低，HPA 不扩容；
- 没有 requests 的 Pod，HPA 无法计算 CPU 利用率；
- HPA 需要 metrics-server（资源指标）和相应权限。

```bash
kubectl get hpa -n prod
kubectl describe hpa web -n prod
kubectl top pods -n prod
```

### 5.2 自定义指标与事件驱动

HPA 支持 `Pods`、`Object`、`External` 指标，需要自定义指标适配器（如 Prometheus Adapter）。事件驱动、队列长度、Kafka lag 等场景可用 KEDA 等方案。

注意：

- 自定义指标必须能反映真实负载，且采集延迟不能太大；
- 扩缩容有延迟（指标采集 + 调度 + 镜像启动 + 预热），不要指望毫秒级响应；
- `behavior` 的稳定窗口避免抖动，但也会延迟缩容；
- 缩容太快会反复扩容，需结合预热和最小副本。

### 5.3 HPA 与 VPA

- HPA 调副本数，VPA 调 requests/limits；
- 两者同时基于 CPU/内存可能冲突；
- VPA 的 `Auto` 更新可能触发 Pod 重启（取决于更新模式）；
- 常见做法：HPA 用 CPU/自定义指标，VPA 只用 recommendation 或 Off 模式辅助容量规划。

## 6. 节点扩缩容

Pod 因资源不足 Pending 时，Cluster Autoscaler/Karpenter 等可根据待调度 Pod 扩容节点。

```text
Pending Pod（Insufficient cpu）
   → 节点组扩容
   → 新节点 Ready
   → 调度器重新调度
```

常见不扩容原因：

- 节点组达到最大容量；
- Pod requests 大于任何可用实例规格；
- 节点亲和性/污点/拓扑约束无法满足；
- 存储卷可用区不匹配；
- 扩容权限/云配额不足；
- 集群没有安装节点自动扩缩器。

缩容时要注意：

- 节点上的 Pod 是否能被驱逐（PDB、本地存储、DaemonSet）；
- 缩容后是否仍有足够副本；
- 刚扩容又缩容的“抖动”；
- 使用 `cluster-autoscaler.kubernetes.io/safe-to-evict` 等注解要谨慎。

## 7. PDB：保护自愿中断

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
  namespace: prod
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: web
```

- 只约束**自愿中断**（`kubectl drain`、节点维护、部分升级），不约束节点宕机、OOM、滚动更新；
- `minAvailable` 与 `maxUnavailable` 二选一；
- selector 必须匹配目标 Pod；
- PDB 太严格会导致 drain 永久阻塞，维护前要评估副本数与拓扑。

```bash
kubectl get pdb -n prod
kubectl describe pdb web-pdb -n prod
```

## 8. 调度排障

Pod `Pending` 时：

```bash
kubectl describe pod <pod> -n prod
kubectl get events -n prod --sort-by=.lastTimestamp
kubectl get nodes -o wide --show-labels
kubectl describe node <node>
```

重点看 Events：

- `Insufficient cpu/memory`：资源不足或 requests 过大；
- `node(s) had untolerated taint`：污点不匹配；
- `node(s) didn't match Pod's node affinity/selector`：标签/亲和性错误；
- `node(s) didn't have free ports`：hostPort 冲突；
- `volume node affinity conflict`：PV 与节点拓扑不匹配；
- `pod has unbound immediate PersistentVolumeClaims`：PVC 未绑定。

```bash
kubectl top nodes
kubectl describe node <node> | sed -n '/Allocated resources/,/Events/p'
```

`Allocated resources` 是 requests 的汇总，不等于实际使用率。节点看起来“很闲”但仍无法调度，通常是因为 requests 已被预留完。

## 9. 容量规划清单

- [ ] 每个容器都有 requests，关键服务有合理 limits；
- [ ] requests 基于真实 P95/P99，而不是拍脑袋；
- [ ] 区分在线服务、批处理、旁路组件的 QoS；
- [ ] 节点预留系统资源，避免系统进程与业务争抢；
- [ ] 多可用区拓扑分布，避免单点；
- [ ] HPA 的 min/max、指标、behavior 经过压测；
- [ ] 节点自动扩缩容有上限和告警；
- [ ] PDB 与维护窗口匹配；
- [ ] 定期检查资源利用率与超卖比例；
- [ ] 用 `kubectl top`、Prometheus、成本数据交叉验证。

## 10. 小结

调度与弹性伸缩是一个闭环：**requests 决定能否调度，limits 决定运行边界，指标决定是否扩容，节点容量决定扩容能否落地**。不要只盯 HPA 的副本数，也要看 requests 配置、调度事件、节点资源和应用启动时间；否则“自动扩容”可能只是把 Pending 的 Pod 变得更多。
