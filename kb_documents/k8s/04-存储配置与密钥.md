# Kubernetes 存储、ConfigMap 与 Secret 实践

> 一句话结论：容器文件系统是临时的，**有状态数据必须落到 Volume/PVC**；配置与密钥要区分“启动时注入”和“运行时可更新”，否则会出现“改了 ConfigMap 但 Pod 没生效”的困惑。

## 1. Volume 的基本模型

Pod 中的 Volume 定义在 `spec.volumes`，由容器通过 `volumeMounts` 挂载：

```yaml
spec:
  volumes:
    - name: cache
      emptyDir:
        sizeLimit: 1Gi
  containers:
    - name: app
      image: registry.example.com/app:1.2.3
      volumeMounts:
        - name: cache
          mountPath: /var/cache/app
```

常见类型：

| 类型 | 生命周期 | 适用场景 |
| --- | --- | --- |
| `emptyDir` | 随 Pod 删除而删除 | 临时缓存、容器间共享文件 |
| `hostPath` | 与节点绑定 | 特殊系统代理/监控；普通业务避免 |
| `configMap` / `secret` | 由对象管理 | 配置文件、证书、密钥 |
| `persistentVolumeClaim` | 独立于 Pod | 数据库、对象存储、持久化数据 |
| CSI 临时卷 | 随 Pod 删除 | 按需挂载的云盘/密钥 |

`emptyDir.medium: Memory` 使用内存，会计入 Pod 内存使用；设置 `sizeLimit` 防止无限增长。

`hostPath` 会带来节点耦合、权限和安全风险，除非是 DaemonSet 类系统组件，否则优先使用 PVC。

## 2. PV、PVC 与 StorageClass

```text
Pod → PVC（我要什么）
        │
        ├─ 静态：绑定已有 PV
        └─ 动态：StorageClass 调用 CSI 创建 PV
```

### 2.1 PVC

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
  namespace: prod
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast
  resources:
    requests:
      storage: 20Gi
```

### 2.2 StorageClass

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
provisioner: csi.example.com
parameters:
  type: ssd
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
```

关键字段：

- `provisioner`：实际创建卷的 CSI 驱动；
- `reclaimPolicy`：PVC 删除后 PV 如何处理，`Delete` 自动删除后端卷，`Retain` 保留供人工恢复；
- `allowVolumeExpansion`：是否允许扩容 PVC；
- `volumeBindingMode`：
  - `Immediate`：PVC 创建即绑定，可能出现“卷在一个区、Pod 调度到另一个区”的冲突；
  - `WaitForFirstConsumer`：等 Pod 调度后再创建卷，适合有拓扑约束的云盘；
- `parameters`：驱动相关，因云厂商/存储系统而异。

### 2.3 访问模式

| 模式 | 含义 | 常见实现 |
| --- | --- | --- |
| `ReadWriteOnce`（RWO） | 单节点读写 | 云盘、本地盘 |
| `ReadOnlyMany`（ROX） | 多节点只读 | 共享文件系统 |
| `ReadWriteMany`（RWX） | 多节点读写 | NFS、CephFS、EFS 等 |
| `ReadWriteOncePod`（RWOP） | 单 Pod 读写 | 较新版本，需驱动支持 |

**RWO 是“单节点”，不是“单 Pod”**：同一节点上的多个 Pod 可能都能挂载同一个 RWO 卷。需要严格单 Pod 独占时，评估 `ReadWriteOncePod` 或应用层锁。

### 2.4 绑定与排障

```bash
kubectl get pvc -n prod
kubectl get pv
kubectl describe pvc data -n prod
kubectl get storageclass
```

PVC 长期 `Pending` 常见原因：

- StorageClass 不存在或不是默认；
- 没有匹配的 PV（静态供应）；
- 后端容量不足/配额不足；
- 访问模式不支持；
- 拓扑不匹配（`WaitForFirstConsumer` 下 Pod 未调度）；
- CSI 驱动未安装或异常。

## 3. StatefulSet 与稳定存储

StatefulSet 为每个副本提供稳定序号、稳定网络标识和独立 PVC：

```yaml
apiVersion: v1
kind: Service
metadata:
  name: db-headless
  namespace: prod
spec:
  clusterIP: None
  selector:
    app.kubernetes.io/name: db
  ports:
    - name: postgres
      port: 5432
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
  namespace: prod
spec:
  serviceName: db-headless
  replicas: 3
  podManagementPolicy: OrderedReady
  selector:
    matchLabels:
      app.kubernetes.io/name: db
  template:
    metadata:
      labels:
        app.kubernetes.io/name: db
    spec:
      containers:
        - name: postgres
          image: postgres:16
          ports:
            - name: postgres
              containerPort: 5432
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: fast
        resources:
          requests:
            storage: 50Gi
```

特点：

- Pod 名稳定：`db-0`、`db-1`、`db-2`；
- DNS：`db-0.db-headless.prod.svc.cluster.local`；
- 每个 Pod 一个 PVC，删除/重建 Pod 会复用原 PVC；
- 默认按顺序创建/更新/删除，`OrderedReady`；
- 缩容不会自动删除 PVC，避免误删数据，但也可能留下孤儿卷，需要人工清理策略。

有状态应用的真正难点不在 YAML，而在**备份、恢复、主从切换、数据一致性、版本升级**。StatefulSet 只提供身份和存储编排，不替代数据库运维。

## 4. 存储扩容与快照

### 4.1 扩容

```yaml
spec:
  resources:
    requests:
      storage: 50Gi
```

前提：

- StorageClass 允许 `allowVolumeExpansion: true`；
- CSI 驱动支持在线扩容；
- 文件系统扩容可能需要重启 Pod 或由驱动完成；
- 不能缩容 PVC。

### 4.2 快照

VolumeSnapshot 依赖 CSI 快照 CRD：

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: db-20261111
  namespace: prod
spec:
  volumeSnapshotClassName: csi-snapclass
  source:
    persistentVolumeClaimName: data-db-0
```

注意：

- 快照是存储层一致性，不等于应用一致性；数据库应先做 checkpoint/备份或使用专用备份工具；
- 快照可能占用后端容量，需设置保留策略；
- 跨集群/跨区域恢复能力取决于驱动；
- 定期做恢复演练，不要只验证“快照创建成功”。

## 5. ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: prod
data:
  app.yaml: |
    server:
      port: 8080
    log:
      level: info
  LOG_LEVEL: info
```

### 5.1 注入方式

**环境变量：**

```yaml
env:
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: LOG_LEVEL
```

`envFrom` 可以批量注入整个 ConfigMap，但要求所有 key 都是合法的环境变量名；像 `app.yaml` 这种文件名 key 会被跳过并产生事件，适合用 Volume 挂载而不是 `envFrom`。

**挂载为文件：**

```yaml
volumes:
  - name: config
    configMap:
      name: app-config
containers:
  - name: app
    volumeMounts:
      - name: config
        mountPath: /etc/app
        readOnly: true
```

### 5.2 更新行为

- **环境变量**：Pod 启动时注入，ConfigMap 更新后不会变化，必须重建 Pod；
- **Volume 挂载**：kubelet 会周期性同步，最终更新（有延迟），但应用是否重新加载取决于自身；
- **`subPath` 挂载**：不会接收 ConfigMap 更新，这是常见坑；
- **`immutable: true`**：禁止修改，需创建新对象并更新引用，适合稳定配置和减少 apiserver 压力。

```yaml
volumes:
  - name: config
    configMap:
      name: app-config
      items:
        - key: app.yaml
          path: app.yaml
```

如果应用不支持热加载，可在 Deployment 的 Pod 模板上加配置校验和注解，触发滚动更新：

```yaml
metadata:
  annotations:
    checksum/config: "<sha256-of-config>"
```

由 CI/ Helm/Kustomize 生成校验和，配置变更时自动滚动。

### 5.3 限制

- ConfigMap 不适合放二进制大文件；
- 单个对象受 etcd 请求大小限制（通常 1 MiB 量级），大配置应放对象存储/配置中心；
- 不要把敏感信息放 ConfigMap；
- 修改 ConfigMap 不会自动回滚应用，需配套发布流程。

## 6. Secret

### 6.1 创建

```bash
kubectl create secret generic app-secret \
  --namespace prod \
  --from-literal=DB_PASSWORD='***' \
  --from-file=tls.crt=./tls.crt \
  --from-file=tls.key=./tls.key
```

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
  namespace: prod
type: Opaque
stringData:
  DB_PASSWORD: "***"
```

`stringData` 会在写入时自动 base64 编码；`data` 字段则要求预先 base64 编码。

### 6.2 Secret 不是“加密保险箱”

默认情况下，Secret 只是 base64 编码，**不是加密**。能读取 Secret 的用户/ServiceAccount 就能拿到明文。必须配合：

- **etcd 静态加密**：配置 `EncryptionConfiguration`，保护 etcd 磁盘/备份；
- **RBAC 最小权限**：限制 `get/list/watch secrets`，这是高权限操作；
- **传输 TLS**：apiserver、kubelet、etcd 之间启用 TLS；
- **外部密钥管理**：External Secrets Operator、Secrets Store CSI Driver、Vault 等；
- **GitOps 加密**：Sealed Secrets、SOPS，避免明文进 Git；
- **轮换**：数据库密码、TLS 证书、Token 定期轮换；
- **审计**：记录 Secret 访问。

### 6.3 注入方式与风险

```yaml
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: app-secret
        key: DB_PASSWORD
```

```yaml
volumes:
  - name: secret
    secret:
      secretName: app-secret
      defaultMode: 0400
```

- 环境变量可能被进程、崩溃转储、日志、子进程泄漏；
- 挂载文件权限更可控，但应用要支持从文件读取；
- `automountServiceAccountToken: false` 可减少不必要的 Token 暴露；
- 不要把 Secret 打印到 CI 日志或 `kubectl describe` 输出中；
- `imagePullSecrets` 只用于拉取私有镜像，和业务 Secret 分开管理。

### 6.4 更新行为

与 ConfigMap 类似：

- 环境变量不会自动更新；
- Volume 挂载最终会更新，但应用需重新加载；
- `subPath` 不会更新；
- TLS Secret 被 Ingress Controller 监听后通常会自动生效，但取决于控制器；
- 数据库密码轮换需要应用支持双密码/平滑切换。

## 7. Projected Volume 与 Downward API

将多个来源投射到同一目录：

```yaml
volumes:
  - name: projected
    projected:
      sources:
        - configMap:
            name: app-config
        - secret:
            name: app-secret
        - downwardAPI:
            items:
              - path: pod-name
                fieldRef:
                  fieldPath: metadata.name
        - serviceAccountToken:
            path: token
            expirationSeconds: 3600
            audience: api
```

适合需要把配置、密钥、Pod 元数据组合挂载的场景；Token 投射可设置过期时间和受众，减少长期凭证风险。

## 8. 权限与安全

```yaml
securityContext:
  runAsUser: 10001
  runAsGroup: 10001
  fsGroup: 10001
  fsGroupChangePolicy: OnRootMismatch
```

- `fsGroup` 让卷对 Pod 组可写，但并非所有 CSI 驱动都支持；
- 只读根文件系统时，需要写入的路径挂 `emptyDir`/PVC；
- 不要在容器内以 root 写共享卷；
- 对共享 RWX 卷，应用层要处理并发写和文件锁；
- 定期扫描 PVC 使用率、 orphan PV、快照保留。

## 9. 检查清单

- [ ] 有状态数据是否使用 PVC，而不是容器文件系统？
- [ ] StorageClass 的回收策略、扩容、拓扑模式是否符合预期？
- [ ] 是否理解 RWO 是节点级而不是 Pod 级？
- [ ] StatefulSet 缩容后的 PVC 如何处理？
- [ ] ConfigMap/Secret 更新后应用是否会重新加载？
- [ ] 是否误用了 `subPath` 导致配置不更新？
- [ ] Secret 是否启用 etcd 加密、RBAC、轮换和审计？
- [ ] 是否做过 PVC 恢复/快照恢复演练？
- [ ] 大配置是否超出 etcd 对象大小限制？

## 10. 小结

存储的关键是生命周期与访问语义：Pod 会漂移，PVC 不会；RWO 绑定节点，不绑定 Pod；动态供应简化了创建，但回收策略和拓扑约束必须明确。配置与密钥的关键是更新语义：环境变量是启动快照，Volume 可能最终更新，`subPath` 不会更新。把这些边界设计清楚，才能避免“配置改了但没生效”和“数据随 Pod 一起消失”。
