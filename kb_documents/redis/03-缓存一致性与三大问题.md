# Redis 缓存一致性、穿透/击穿/雪崩与热 key 治理

> 一句话结论：缓存与数据库之间不存在“免费强一致”。工程上要做的是**明确一致性等级、缩小不一致窗口、保证最终可恢复**，并用监控证明效果。

## 1. 先选缓存模式

### 1.1 Cache-Aside（旁路缓存）

最常见：

```text
读：查缓存 → 命中返回
           → 未命中查数据库 → 回填缓存

写：更新数据库 → 删除缓存
```

优点：实现简单、缓存只存热点数据、数据库是事实来源。
缺点：读写并发时存在短暂不一致；删除失败会留下旧值。

### 1.2 Read-Through / Write-Through

由缓存层负责回源和写库，应用只与缓存交互。适合有统一数据访问层的系统，但实现复杂，写穿透会增加延迟。

### 1.3 Write-Behind

先写缓存，异步批量写数据库。吞吐高，但故障时可能丢数据，通常只适合可容忍丢失的场景（如计数、埋点）。

**结论**：大多数业务用 Cache-Aside；强一致要求高的核心账务数据不应把 Redis 当事实来源。

## 2. 为什么“更新数据库 + 删除缓存”仍会不一致

考虑以下时序：

```text
T1 读请求：缓存未命中，从数据库读到旧值 V1
T2 写请求：更新数据库为 V2，删除缓存
T3 读请求：把 V1 写回缓存
结果：缓存长期是 V1，直到 TTL 到期
```

这是典型的“读回填覆盖删除”。常见缓解手段：

1. **给缓存设置合理 TTL**：最终一致兜底；
2. **延迟双删**：更新数据库后删除一次，延迟几百毫秒再删除一次；
3. **读请求加分布式锁/单飞**：同一 key 的并发回填只允许一个请求，且回填前再次校验版本；
4. **版本号/时间戳**：缓存值携带版本，回填时用 Lua 比较，旧版本不覆盖新版本；
5. **binlog/CDC 驱动删除**：订阅数据库变更，异步删除缓存，避免业务代码漏删；
6. **写后短时间读主库**：对一致性敏感的读请求绕过缓存。

### 2.1 延迟双删示例

```pseudo
update_database(...)
delete_cache(key)
sleep(300ms)          // 覆盖大多数并发回填窗口
delete_cache(key)
```

延迟时间无法对所有并发场景给出一劳永逸的值，且会引入异步任务与失败重试。它降低概率，不提供严格证明。

### 2.2 版本比较写入

```lua
-- KEYS[1]=cache key, ARGV[1]=new value, ARGV[2]=new version
local old = redis.call("GET", KEYS[1])
if old then
  local ok, obj = pcall(cjson.decode, old)
  if ok and obj.version and tonumber(obj.version) >= tonumber(ARGV[2]) then
    return 0
  end
end
redis.call("SET", KEYS[1], ARGV[1], "EX", 3600)
return 1
```

版本号必须来自数据库的单调递增字段（如 `updated_at` + 自增版本），否则多节点时钟不可靠。

### 2.3 先删缓存还是先更新数据库？

| 策略 | 风险 |
| --- | --- |
| 先删缓存，再更新数据库 | 更新完成前有读请求回填旧值，且提交失败会留下不一致 |
| 先更新数据库，再删缓存 | 删除失败或并发回填会留下旧值；通常更推荐 |
| 更新数据库，再更新缓存 | 并发写可能乱序，旧值覆盖新值；计算复杂时更明显 |

没有一种顺序能无条件保证强一致。**优先“更新数据库 + 删除缓存 + TTL + 重试/CDC”**，并根据业务接受度补充读主库、版本控制等策略。

## 3. 缓存穿透

### 3.1 现象

请求查询不存在的数据，缓存永远不命中，压力全部打到数据库。常见于恶意扫描、非法 ID、被删除的数据。

### 3.2 方案

1. **空值缓存**：数据库查不到也缓存一个短 TTL 的空标记。
   ```redis
   SET product:not-exist:9999 "__NULL__" EX 60
   ```
   注意：数据后来被创建时要能删除空标记，否则会短暂“看不见”。
2. **布隆过滤器**：在缓存前判断 key 是否可能存在；不存在直接拒绝。布隆过滤器有假阳性、无删除（计数布隆可删除但更复杂），需要定期重建。
3. **参数校验与限流**：ID 格式、范围、签名校验；对异常来源限流。
4. **接口层防刷**：验证码、风控、黑名单。

组合使用效果最好：布隆过滤 + 空值缓存 + 限流。

## 4. 缓存击穿

### 4.1 现象

某个热点 key 过期瞬间，大量并发请求同时未命中，全部回源数据库，可能压垮数据库。

### 4.2 方案

**方案 A：互斥重建（单飞）**

```pseudo
value = cache.get(key)
if value != null:
    return value

if cache.set(key + ":lock", token, NX, PX=3000):
    try:
        value = db.query(key)
        cache.set(key, value, ttl=300 + rand(60))
        return value
    finally:
        release_lock_if_token_matches(key + ":lock", token)
else:
    sleep(50ms)
    return cache.get(key) or fallback()
```

注意锁的超时、续期、释放原子性，以及等待方的超时与降级。

**方案 B：逻辑过期**

缓存值不设物理 TTL，内部存 `expire_at`。发现逻辑过期时，一个线程异步重建，其他请求先返回旧值（stale-while-revalidate）。适合能接受短时旧值的场景。

**方案 C：热点数据预热 + 永不过期 + 后台刷新**

需要保证刷新任务可靠，并有版本控制防止旧数据覆盖。

## 5. 缓存雪崩

### 5.1 现象

大量 key 在同一时间过期，或 Redis 整体故障，导致请求瞬间涌向数据库。

### 5.2 方案

- **TTL 加随机抖动**：`base_ttl + random(0, jitter)`，避免整点集体失效；
- **多级缓存**：本地缓存 + Redis，Redis 故障时本地仍可挡一部分；
- **熔断与限流**：数据库压力过大时快速失败或返回降级数据；
- **高可用**：主从/Sentinel/Cluster，避免单点；
- **预热**：发布、扩容、重启后先加载热点数据；
- **隔离**：不同业务使用不同实例/集群，避免相互影响；
- **异步重建**：后台刷新，减少同步回源。

降级不是“假装成功”，要明确返回旧值、默认值还是错误码，并让前端可处理。

## 6. 热 key 与大 key

### 6.1 热 key

某个 key 的 QPS 远高于其他 key，可能打满单个 Redis 节点或网络带宽。

识别：

```bash
# 需要 LFU 策略，且采样有 overhead
redis-cli --hotkeys

# 单 key 访问统计（部分托管服务提供）
redis-cli OBJECT FREQ hot:key
```

治理：

- **本地缓存**：极热数据放应用进程内，设置短 TTL；
- **key 拆分**：`hot:key:0..N` 分散到不同 slot，读时随机/轮询；
- **读写分离**：从副本读，但接受复制延迟；
- **请求合并**：单飞、批量接口；
- **限流与隔离**：避免一个热点拖垮整个实例。

### 6.2 大 key

String 过大、Hash/List/Set/ZSet 元素过多，都会导致网络阻塞、删除卡顿、迁移困难。

治理：

- 拆分：按业务维度分桶，如 `user:1001:profile:basic`、`user:1001:profile:ext`；
- 压缩：JSON 压缩、协议优化；
- 控制集合长度：List `LTRIM`、Stream `MAXLEN`；
- 删除用 `UNLINK`，并监控内存回收；
- 迁移/备份前评估大 key 的耗时；
- 用 `MEMORY USAGE`、`--bigkeys` 定期扫描。

## 7. 分布式锁：别把它当万能一致性方案

基本安全实现：

```text
SET lock:order:1001 <unique-token> NX PX 30000
```

释放必须原子校验 token：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
end
return 0
```

仍需考虑：

- **业务执行超过锁租期**：需要看门狗续期，或把锁租期设得足够长；
- **主从切换丢锁**：异步复制下，锁可能在新主上不存在；
- **GC/网络停顿**：客户端持有锁但实际已超时；
- ** fencing token**：下游资源校验单调递增的令牌，拒绝过期持有者的写入，这是比“锁是否还在”更强的保护；
- **Redlock 争议**：多实例 Redlock 在极端时钟/网络条件下仍有争议；强一致场景优先数据库行锁、etcd/ZooKeeper 或带 fencing 的设计。

分布式锁适合“减少重复工作”，不应单独承担资金安全等强一致职责。

## 8. 限流示例：固定窗口与滑动窗口

```lua
-- 固定窗口限流：KEYS[1]=rate:api:user:1001:202611112030
-- ARGV[1]=limit, ARGV[2]=window_seconds
local current = redis.call("INCR", KEYS[1])
if current == 1 then
  redis.call("EXPIRE", KEYS[1], ARGV[2])
end
if current > tonumber(ARGV[1]) then
  return 0
end
return 1
```

固定窗口在边界可能放过双倍流量；滑动窗口可用 ZSet 记录时间戳，或使用令牌桶 Lua。限流 key 要设置过期，避免内存泄漏。

## 9. 监控与验收

| 指标 | 说明 |
| --- | --- |
| 缓存命中率 | `keyspace_hits / (hits + misses)`，按业务分组更有意义 |
| 回源 QPS | 缓存失效时数据库压力 |
| `evicted_keys` | 是否因内存不足被淘汰 |
| `expired_keys` | 过期 key 速率 |
| `used_memory` / 碎片率 | 容量与内存健康 |
| 命令延迟 P99 | 是否受慢命令/大 key 影响 |
| 热 key / 大 key 数量 | 定期治理 |
| 数据库连接数/慢查询 | 缓存失效的连锁反应 |

验收缓存方案时，至少模拟：

- Redis 整体不可用；
- 热点 key 同时过期；
- 大量不存在的 key 请求；
- 主从切换/网络抖动；
- 缓存与数据库短暂不一致。

## 10. 小结

缓存一致性是**概率与时间窗口**的工程问题：TTL 提供最终兜底，删除策略缩小窗口，版本/锁/CDC 处理关键路径，监控验证真实效果。穿透、击穿、雪崩分别对应“查不存在”“热点过期”“大面积失效”，治理思路分别是**拦截、单飞/逻辑过期、分散 TTL + 降级 + 高可用**。
