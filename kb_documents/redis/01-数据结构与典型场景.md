# Redis 数据结构、底层编码与典型场景

> 一句话结论：Redis 的“快”来自内存、高效数据结构和单线程命令模型；用好它的关键，是**为访问模式选择正确的类型**，并避免大 key、热 key 和 O(N) 命令。

## 1. 一张图理解 Redis

```text
客户端 ──► 连接 ──► 命令队列 ──► 单线程执行命令 ──► 内存数据结构
                                      │
                                      ├─► RDB / AOF 持久化
                                      └─► 主从复制 / Cluster
```

Redis 的命令执行主流程是单线程的（网络 I/O 在较新版本可由多线程处理，但命令执行仍按顺序），因此：

- 单条命令天然原子；
- 一条慢命令会阻塞后续所有请求；
- 不要把 Redis 当成需要复杂计算的关系型数据库；
- 多命令“原子性”需要 Lua、事务或单命令设计来保证。

## 2. 五种基础类型

### 2.1 String：缓存、计数、分布式锁

底层是 SDS（简单动态字符串），根据内容可能是 `int`、`embstr` 或 `raw` 编码。

```redis
SET user:1001:name "Alice" EX 3600
GET user:1001:name
INCR article:2001:views
SETNX lock:order:1001 "token-abc"
```

典型场景：

- 对象缓存（JSON 序列化）；
- 计数器（`INCR`/`INCRBY`）；
- 分布式锁（`SET key token NX PX 30000`）；
- 位图（Bitmap）存储签到、活跃状态。

注意：

- 大字符串（几十 MB）会拖慢网络和持久化；
- `APPEND`、`SETRANGE` 可能触发扩容与拷贝；
- 分布式锁的释放必须校验 token，不能直接 `DEL`：

```lua
-- KEYS[1] = lock key, ARGV[1] = token
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```

### 2.2 Hash：对象属性

小 Hash 使用 listpack（旧版本为 ziplist），字段多或值大时转为 hashtable。

```redis
HSET user:1001 name "Alice" age 30 city "Shanghai"
HGET user:1001 name
HINCRBY user:1001 age 1
HGETALL user:1001
```

适合存放对象的多个字段，便于单独更新。但要注意：

- `HGETALL` 在大 Hash 上是 O(N)，会阻塞；
- 遍历用 `HSCAN`；
- 字段数量特别多的 Hash 属于大 key，考虑拆分。

### 2.3 List：队列与时间线

底层为 quicklist（由多个 listpack 节点组成的双向链表），兼顾内存与操作效率。

```redis
LPUSH queue:jobs "job-1"
BRPOP queue:jobs 5
LRANGE feed:1001 0 9
LTRIM feed:1001 0 999
```

典型场景：

- 简单队列：`LPUSH` + `BRPOP`；
- 最新列表/时间线：`LPUSH` + `LTRIM`；
- 栈：同端 `LPUSH`/`LPOP`。

局限：

- List 没有消费确认机制，消费者崩溃会丢任务；
- 需要重试、死信、消费组时，优先使用 **Stream**；
- 队列长度要做上限，避免无限增长。

### 2.4 Set：去重、交并差

小整数集合使用 intset，小集合可能使用 listpack，大集合使用 hashtable。

```redis
SADD article:2001:likes 1001 1002 1003
SISMEMBER article:2001:likes 1001
SINTER user:1001:follows user:1002:follows
SUNIONSTORE feed:merge feed:a feed:b
```

典型场景：

- 标签、点赞用户、抽奖参与者；
- 共同关注、推荐候选集；
- 去重统计（注意集合大小）。

`SMEMBERS` 在大集合上是 O(N)，线上遍历应使用 `SSCAN`。

### 2.5 ZSet：排行榜、延迟队列

小 ZSet 使用 listpack，大 ZSet 使用 skiplist + hashtable。跳表支持按分数范围查询和排名，哈希表支持按成员查分数。

```redis
ZADD leaderboard 1200 "alice" 980 "bob"
ZINCRBY leaderboard 50 "alice"
ZREVRANGE leaderboard 0 9 WITHSCORES
ZRANGE leaderboard 1000 2000 BYSCORE LIMIT 0 10
```

典型场景：

- 排行榜；
- 延迟队列：score 存执行时间戳，轮询 `ZRANGEBYSCORE` 到期任务；
- 滑动窗口限流：score 存时间戳，统计窗口内数量。

## 3. 进阶类型

### 3.1 Bitmap

用 String 的位操作记录布尔状态，极省内存。

```redis
SETBIT sign:1001:202611 11 1
GETBIT sign:1001:202611 11
BITCOUNT sign:1001:202611
```

适合签到、活跃用户、布隆过滤器位图。注意偏移量过大时会分配大量内存。

### 3.2 HyperLogLog

概率基数统计，标准误差约 0.81%，内存固定约 12 KB。

```redis
PFADD uv:20261111 user-1 user-2 user-3
PFCOUNT uv:20261111
PFMERGE uv:week uv:20261110 uv:20261111
```

适合 UV 估算，不适合需要精确用户列表的场景。

### 3.3 GEO

基于 ZSet 的地理位置索引。

```redis
GEOADD shops 121.4737 31.2304 "shop:1"
GEOSEARCH shops FROMMEMBER "shop:1" BYRADIUS 5 km ASC
```

### 3.4 Stream：可靠消息队列

```redis
XADD orders * order_id 1001 amount 99.00
XGROUP CREATE orders order-workers 0 MKSTREAM

XREADGROUP GROUP order-workers worker-1 COUNT 10 BLOCK 5000 STREAMS orders >
XACK orders order-workers 1700000000000-0
XPENDING orders order-workers
XAUTOCLAIM orders order-workers worker-2 60000 0-0 COUNT 10
```

Stream 支持消费组、ACK、待处理列表和消息转移，比 List 队列更适合业务消息。但它不是 Kafka：没有分区副本的强语义，容量与留存要显式控制（`MAXLEN`/`MINID`）。

### 3.5 Pub/Sub

发布订阅是“即发即忘”，不在线就丢消息，不适合可靠事件总线。需要可靠投递时用 Stream 或专业消息队列。

## 4. 底层编码与查看方式

Redis 会根据元素数量和值大小自动切换编码，以平衡内存与操作复杂度：

| 类型 | 常见编码 | 特点 |
| --- | --- | --- |
| String | `int` / `embstr` / `raw` | 短字符串常与对象一起分配 |
| Hash | `listpack` / `hashtable` | 小对象紧凑，大对象 O(1) 查找 |
| List | `quicklist` / `listpack` | 分块链表，避免超大连续内存 |
| Set | `intset` / `listpack` / `hashtable` | 整数集合紧凑，大集合转哈希 |
| ZSet | `listpack` / `skiplist` | 小集合紧凑，大集合支持范围与排名 |

```redis
OBJECT ENCODING user:1001
MEMORY USAGE user:1001 SAMPLES 0
```

编码阈值由 `*-max-listpack-size`、`*-max-listpack-entries` 等参数控制，不同版本默认值可能变化。不要依赖具体编码做业务逻辑，只把它当作性能诊断信息。

## 5. 命令复杂度与阻塞风险

| 命令 | 复杂度 | 风险 |
| --- | --- | --- |
| `GET` / `SET` | O(1) | 大 value 带来网络与内存压力 |
| `HGETALL` | O(N) | 大 Hash 阻塞 |
| `SMEMBERS` | O(N) | 大 Set 阻塞 |
| `KEYS` | O(N) | 全库扫描，生产禁用 |
| `FLUSHALL` / `FLUSHDB` | O(N) | 删除大量 key 时阻塞 |
| `SORT` | O(N log N) | 大集合昂贵 |
| `ZRANGE` 大范围 | O(log N + M) | 返回元素过多 |
| Lua 长脚本 | 阻塞 | 脚本执行期间其他命令无法执行 |

替代方案：

```redis
SCAN 0 MATCH user:* COUNT 1000
HSCAN user:1001 0 COUNT 100
SSCAN article:2001:likes 0 COUNT 100
UNLINK big:key
```

`SCAN` 是渐进式遍历，不保证在扩容/缩容期间返回所有元素，但不会像 `KEYS` 一样长时间阻塞。

## 6. Key 设计规范

推荐结构：

```text
业务:对象:ID:字段
order:1001:detail
user:1001:profile
rate:api:20261111:1001
```

原则：

- 可读、可定位、避免无意义长 key；
- 控制 key 数量，避免百万级小 key 带来元数据开销；
- 统一 TTL 策略，避免大量 key 同时过期；
- 大 key 拆分（Hash 分桶、List 分页、Set 按业务分片）；
- 热 key 做本地缓存、多副本或 key 拆分；
- 不使用 `KEYS` 做线上扫描；
- 删除大 key 用 `UNLINK`（异步释放）并评估内存回收速度。

## 7. 发现大 key 与热 key

```bash
# 抽样统计大 key（离线/低峰执行）
redis-cli --bigkeys

# 需要 LFU 淘汰策略才能较好统计热 key
redis-cli --hotkeys

# 查看单个 key 内存
redis-cli MEMORY USAGE order:1001:detail SAMPLES 0

# 慢日志
redis-cli SLOWLOG GET 20
```

`MONITOR` 会显著影响性能，只能短时间排障。生产更推荐用代理层指标、客户端埋点或 `redis-cli --hotkeys`（需要 `maxmemory-policy allkeys-lfu` 或 `volatile-lfu`）。

## 8. 事务、Lua 与原子性

```redis
MULTI
INCR account:1:balance
DECR account:2:balance
EXEC
```

Redis 事务：

- 命令入队，`EXEC` 时顺序执行；
- 不会回滚运行时错误（例如对字符串执行 `INCR`）；
- 不具备关系型数据库的隔离级别语义。

需要“读-判断-写”原子性时，优先使用 Lua：

```lua
-- 原子扣减库存，返回剩余库存；不足返回 -1
local stock = tonumber(redis.call("GET", KEYS[1]) or "0")
local qty = tonumber(ARGV[1])
if stock < qty then
  return -1
end
return redis.call("DECRBY", KEYS[1], qty)
```

Lua 脚本应短小、避免循环处理大量元素；Cluster 下所有 key 必须位于同一 slot。

## 9. 选型速查

| 需求 | 推荐结构 | 备注 |
| --- | --- | --- |
| 对象缓存 | String / Hash | 整体读写用 String，字段更新用 Hash |
| 计数器 | String | `INCR` 原子 |
| 排行榜 | ZSet | 分数 + 排名 |
| 去重 | Set / Bitmap / HLL | 精确用 Set，估算用 HLL |
| 简单队列 | List / Stream | 可靠消费选 Stream |
| 延迟任务 | ZSet | 注意轮询与并发抢占 |
| 签到 | Bitmap | 控制偏移量 |
| 附近的人 | GEO | 底层 ZSet |
| 限流 | String / ZSet / Lua | 固定窗口/滑动窗口 |

## 10. 小结

选择数据结构时，先问三个问题：**访问模式是什么？数据规模多大？失败与一致性要求是什么？** 然后用 `OBJECT ENCODING`、`MEMORY USAGE`、慢日志和监控验证。Redis 的很多“性能事故”并非容量不足，而是大 key、热 key 或一条 O(N) 命令造成的。
