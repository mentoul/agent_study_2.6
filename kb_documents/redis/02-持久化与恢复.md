# Redis 持久化：RDB、AOF 与可验证的恢复

> 一句话结论：RDB 是“某一刻的快照”，AOF 是“按顺序记录写命令的日志”。选择哪一种，本质上是在 **恢复速度、数据丢失窗口、写入延迟和磁盘占用**之间做权衡。

## 1. RDB：快照

### 1.1 工作方式

`BGSAVE` 会 `fork` 出子进程，子进程把当前内存快照写入临时文件，完成后原子替换 `dump.rdb`。主进程继续处理请求，依靠操作系统的写时复制（Copy-On-Write，COW）隔离内存页。

```ini
# redis.conf
save 3600 1
save 300 100
save 60 10000
dbfilename dump.rdb
dir /var/lib/redis
rdbcompression yes
rdbchecksum yes
stop-writes-on-bgsave-error yes
```

相关命令：

```redis
BGSAVE
LASTSAVE
INFO persistence
```

### 1.2 优点

- 文件紧凑，适合全量备份与跨环境迁移；
- 恢复时直接加载二进制快照，通常比逐条回放 AOF 快；
- 对主进程的持续写入影响较小（但 fork 和 COW 有成本）；
- 可以做定时冷备、异地归档。

### 1.3 缺点

- 两次快照之间的数据会丢失，RPO 取决于 `save` 频率；
- `fork` 在大内存实例上可能造成明显延迟；
- COW 在写入密集时会额外占用内存，最坏情况下接近翻倍；
- 快照期间如果主进程修改大量页，内存压力会升高；
- RDB 文件是二进制格式，不方便做细粒度审计。

### 1.4 触发方式

- 配置 `save` 规则自动触发；
- 客户端执行 `BGSAVE`；
- `SHUTDOWN SAVE`；
- 主从全量同步时生成 RDB（可能走磁盘或 diskless）。

`SAVE` 会阻塞主进程，生产环境不应使用。

## 2. AOF：追加写日志

### 2.1 工作方式

AOF 记录所有写命令（以 RESP 协议格式），Redis 重启时按顺序回放。Redis 7 使用**多部分 AOF**（multi-part AOF）：一个 base 文件加若干 incr 文件，由 manifest 管理，重写时无需再复制整个旧 AOF。

```ini
appendonly yes
appendfilename "appendonly.aof"
appenddirname "appendonlydir"

# 每秒 fsync 一次，兼顾性能与持久性
appendfsync everysec

# AOF 重写触发条件
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# 重写期间是否暂停 fsync（默认 no，更安全）
no-appendfsync-on-rewrite no

# 混合持久化：base 用 RDB 格式，后续追加命令
aof-use-rdb-preamble yes

# 启动时是否容忍尾部截断
aof-load-truncated yes
```

### 2.2 `appendfsync` 三种策略

| 值 | 行为 | 数据丢失窗口 | 性能 |
| --- | --- | --- | --- |
| `always` | 每个写命令都 fsync | 通常最小 | 最差，受磁盘延迟影响大 |
| `everysec` | 后台每秒 fsync | 通常约 1 秒，极端情况可能接近 2 秒 | 折中，生产常用 |
| `no` | 交给操作系统刷盘 | 不可控，可能数十秒 | 最好，但持久性最弱 |

`everysec` 不是“绝对只丢 1 秒”：如果上一次 fsync 尚未完成，Redis 可能延迟下一次 fsync；磁盘抖动、虚拟机迁移、内核问题都会放大窗口。

### 2.3 AOF 重写

AOF 会不断增长，需要通过重写压缩：

```redis
BGREWRITEAOF
```

重写同样依赖 `fork` 和 COW，子进程根据当前内存生成最小命令集，主进程把重写期间的新写命令追加到缓冲区，最后合并。

监控：

```redis
INFO persistence
```

重点字段：

- `aof_enabled`
- `aof_rewrite_in_progress`
- `aof_last_bgrewrite_status`
- `aof_last_write_status`
- `aof_current_size` / `aof_base_size`
- `rdb_last_bgsave_status`
- `latest_fork_usec`

## 3. RDB 与 AOF 如何选

| 维度 | RDB | AOF（everysec） |
| --- | --- | --- |
| RPO | 分钟级（取决于 save） | 秒级 |
| 恢复速度 | 快 | 较慢，取决于日志量 |
| 文件大小 | 小 | 较大 |
| 写入延迟 | 主要受 fork/COW 影响 | 受 fsync 影响 |
| 可读性 | 二进制 | 协议文本，可分析 |
| 适合 | 备份、灾难恢复、可容忍分钟级丢失 | 对数据丢失敏感的业务 |

常见组合：

1. **缓存场景**：只开 RDB，甚至不持久化；数据可从数据库重建。
2. **一般业务**：RDB + AOF `everysec`，兼顾恢复速度与数据安全。
3. **高可靠要求**：AOF `everysec` + 主从 + 定期 RDB 备份 + 恢复演练；对零丢失有强需求时，需要评估 `always` 的性能代价或引入其他存储。
4. **纯备份**：定期 `BGSAVE`，把 RDB 文件归档到异地对象存储。

## 4. 启动时加载哪一个

简化规则：

- `appendonly yes`：优先加载 AOF；
- `appendonly no`：加载 RDB；
- AOF 使用混合格式时，base 可能是 RDB 格式，后续 incr 是命令日志；
- 加载失败时，Redis 可能拒绝启动，需检查日志与文件完整性。

```bash
# RDB
redis-check-rdb /var/lib/redis/dump.rdb

# Redis 6 及更早版本：单文件 AOF
redis-check-aof /var/lib/redis/appendonly.aof
```

Redis 7 使用多部分 AOF（manifest + base + incr）。检查时应针对 `appendonlydir` 下的 manifest/分片文件，具体命令以当前版本的 `redis-check-aof` 帮助为准；不要只复制其中一个 incr 文件就当作完整备份。

如果 AOF 尾部因断电截断，可在确认只丢失尾部少量命令后修复：

```bash
# 先备份整个 AOF 目录，再按版本要求指定 manifest 或 AOF 文件
redis-check-aof --fix <AOF 文件或 manifest>
```

**修复前先复制原文件/整个目录**。`--fix` 会截断不完整部分，可能丢失最后若干写操作，必须评估业务影响。

## 5. 备份的正确姿势

### 5.1 RDB 备份流程

```bash
# 1. 触发快照
redis-cli BGSAVE

# 2. 等待完成并确认状态
watch -n 1 'redis-cli INFO persistence | grep -E "rdb_bgsave_in_progress|rdb_last_bgsave_status"'

# 3. 复制文件（注意配置中的 dir 与 dbfilename）
cp /var/lib/redis/dump.rdb /backup/redis-$(date +%F-%H%M).rdb

# 4. 校验
redis-check-rdb /backup/redis-2026-11-11-0200.rdb
```

更稳妥的做法：

- 在**从库**执行备份，避免主库 fork 抖动；
- 备份前确认从库已追平；
- 备份文件计算 SHA-256，记录元数据（版本、实例、时间、RDB 校验和）；
- 上传到异地对象存储并设置生命周期与不可变策略；
- 不要只保留一份，防止误删、磁盘损坏、勒索软件。

### 5.2 AOF 备份的复杂性

AOF 在运行中持续追加，直接 `cp` 可能得到不一致的尾部。可选方案：

- 使用 RDB 做全量备份，AOF 仅用于实例自身恢复；
- 在从库上暂停写入/停止实例后复制整个 `appendonlydir`；
- 使用文件系统快照（LVM、云盘快照），并确保快照原子性；
- 接受“备份时点”语义，明确 RPO。

Redis 没有像 MySQL binlog 那样成熟的任意时间点回放工具，AOF 的“截断到某个时间点”通常需要人工分析命令流，风险较高。

### 5.3 Cluster 备份

- 每个 master 都要备份；仅备份一个节点无法还原整个集群；
- 同时备份 `nodes.conf`、集群配置、ACL 和 TLS 证书；
- 恢复时先恢复各节点数据，再按原 slot 分配重建集群；
- 记录集群 ID、节点 ID、slot 分布，避免恢复后拓扑错乱。

## 6. fork、内存与内核参数

RDB 和 AOF 重写都依赖 `fork`。大内存实例要特别注意：

```bash
# 允许内存 overcommit，降低 fork 失败概率
sysctl vm.overcommit_memory=1

# 建议关闭透明大页，减少 fork 后的延迟抖动
echo never > /sys/kernel/mm/transparent_hugepage/enabled
```

同时：

- 预留足够内存给 COW，不要把 `maxmemory` 设到物理内存上限；
- 监控 `latest_fork_usec`、`rdb_bgsave_in_progress`、`aof_rewrite_in_progress`；
- 避免在业务高峰做手工 `BGSAVE`/`BGREWRITEAOF`；
- 容器环境要确认内存限制与 overcommit 行为，OOM Killer 可能直接杀掉 Redis；
- 磁盘满会导致持久化失败，`stop-writes-on-bgsave-error yes` 时还会拒绝写入，必须监控。

## 7. 恢复流程

```bash
# 1. 停止 Redis，确认没有进程持有数据目录
systemctl stop redis

# 2. 备份当前损坏/旧数据，避免二次破坏
mv /var/lib/redis /var/lib/redis.bak.$(date +%s)
mkdir -p /var/lib/redis
chown redis:redis /var/lib/redis

# 3. 放入恢复文件
cp /backup/redis-2026-11-11-0200.rdb /var/lib/redis/dump.rdb
chown redis:redis /var/lib/redis/dump.rdb

# 4. 如使用 AOF，恢复整个 appendonlydir，而不是只放一个文件
# cp -a /backup/appendonlydir /var/lib/redis/

# 5. 启动并检查
systemctl start redis
redis-cli INFO persistence
redis-cli DBSIZE
```

恢复后必须验证：

- 关键 key 是否存在、TTL 是否符合预期；
- 数据量、内存占用是否在合理范围；
- 主从复制是否正常；
- 应用读写是否正常；
- 恢复耗时是否满足 RTO。

## 8. 常见故障

### 8.1 启动报 “Bad file format reading the append only file”

可能原因：AOF 尾部截断、磁盘写入损坏、混合格式文件不完整。处理：

1. 备份原文件；
2. 用 `redis-check-aof` 检查；
3. 确认可接受丢失范围后 `--fix`；
4. 若仍失败，考虑用 RDB 备份恢复，或从副本重建。

### 8.2 `MISCONF Redis is configured to save RDB snapshots...`

通常是 `stop-writes-on-bgsave-error yes` 且最近一次 `BGSAVE` 失败。检查磁盘空间、权限、`dir` 路径、fork 是否失败。不要直接关闭该参数掩盖问题。

### 8.3 fork 超时或内存暴涨

检查实例内存、COW、THP、overcommit、容器限制。必要时降低单实例内存、拆分实例、在从库备份。

### 8.4 AOF 文件无限增长

检查 `auto-aof-rewrite-percentage`、`auto-aof-rewrite-min-size` 是否合理，重写是否失败，写入速率是否远超预期。重写失败常见于磁盘空间不足或 fork 失败。

## 9. 检查清单

- [ ] 明确业务 RPO/RTO，并据此选择 RDB/AOF 组合；
- [ ] `appendfsync` 与磁盘性能匹配；
- [ ] 定期验证 RDB/AOF 可加载；
- [ ] 备份在从库执行，且从库已追平；
- [ ] 备份加密、异地、保留策略、恢复演练；
- [ ] 监控持久化状态、fork 耗时、磁盘空间、内存；
- [ ] 升级前验证 RDB/AOF 兼容性，保留回滚路径。

## 10. 小结

RDB 擅长“快速全量恢复”，AOF 擅长“缩小丢失窗口”。生产环境通常不是二选一，而是 **RDB 做备份基线、AOF 做近实时持久化、复制做可用性、演练做最终验收**。任何持久化配置，如果没有经过真实恢复验证，都不能算可靠。
