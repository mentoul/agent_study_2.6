# MySQL 主从复制、半同步与高可用切换

> 一句话结论：复制解决“数据有几份”，高可用解决“故障时谁接管”；两者之间还差**故障检测、选主、 fencing、流量切换和一致性校验**，不能混为一谈。

## 1. 复制的基本链路

```text
应用写入
   │
   ▼
主库：写 binlog ──► dump 线程发送 ──► 从库 IO 线程写入 relay log
                                           │
                                           ▼
                                    从库 SQL 线程回放
                                           │
                                           ▼
                                       从库数据
```

关键日志与线程：

- **binlog**：主库记录所有数据变更（ROW 格式下记录行级前后镜像）；
- **relay log**：从库暂存收到的日志；
- **IO 线程**：连接主库、拉取 binlog；
- **SQL/Applier 线程**：回放 relay log；
- **GTID**：全局事务 ID，使“从哪个位置继续”变成“还缺哪些事务”。

## 2. 推荐的基础配置

主库 `my.cnf` 示例：

```ini
[mysqld]
server_id = 101
log_bin = mysql-bin
binlog_format = ROW
binlog_row_image = FULL
gtid_mode = ON
enforce_gtid_consistency = ON
binlog_expire_logs_seconds = 604800
sync_binlog = 1
innodb_flush_log_at_trx_commit = 1
```

从库额外配置：

```ini
[mysqld]
server_id = 102
relay_log = relay-bin
read_only = ON
super_read_only = ON
log_replica_updates = ON
replica_parallel_workers = 8
replica_parallel_type = LOGICAL_CLOCK
replica_preserve_commit_order = ON
```

说明：

- `server_id` 必须全局唯一，否则复制会中断；
- `ROW` 是生产推荐格式，便于数据校验和恢复；`binlog_row_image=FULL` 兼容性最好，但日志更大；
- `sync_binlog=1` 与 `innodb_flush_log_at_trx_commit=1` 提供较强的持久性，代价是每次提交的刷盘开销；
- `read_only` 不能阻止有 `SUPER` 权限的账号写入，`super_read_only` 更严格；
- 并行回放需要结合负载压测，不是 worker 越多越好。

## 3. 建立 GTID 复制

在主库创建复制账号（最小权限）：

```sql
CREATE USER 'repl'@'10.0.0.%' IDENTIFIED BY 'Use-A-Real-Secret';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'10.0.0.%';
```

从库执行（MySQL 8.0.23+ 语法）：

```sql
STOP REPLICA;

CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = '10.0.0.11',
  SOURCE_PORT = 3306,
  SOURCE_USER = 'repl',
  SOURCE_PASSWORD = 'Use-A-Real-Secret',
  SOURCE_AUTO_POSITION = 1,
  GET_SOURCE_PUBLIC_KEY = 1;

START REPLICA;
```

> 旧版本使用 `CHANGE MASTER TO` / `MASTER_HOST` 等语法。MySQL 8.0.23 起官方术语统一为 SOURCE/REPLICA；实际执行前请按版本确认。

检查：

```sql
SHOW REPLICA STATUS\G
```

重点字段：

| 字段 | 期望 | 异常时看 |
| --- | --- | --- |
| `Replica_IO_Running` | `Yes` | 网络、账号、防火墙、主库 binlog 是否被清理 |
| `Replica_SQL_Running` | `Yes` | `Last_SQL_Error`，常见于主键冲突、数据不一致 |
| `Seconds_Behind_Source` | 接近 0 | 大事务、DDL、单线程瓶颈、从库资源不足 |
| `Retrieved_Gtid_Set` | 持续增长 | IO 线程是否卡住 |
| `Executed_Gtid_Set` | 追平主库 | SQL 线程是否积压 |
| `Auto_Position` | `1` | 是否使用 GTID 自动定位 |

`Seconds_Behind_Source` 并不是精确延迟：它基于事件时间戳，主库长时间无写入时可能显示 0，但实际并未验证最新事务。更可靠的方式是比较 GTID 集合，或在业务写入后主动探测。

```sql
-- 主库
SELECT @@GLOBAL.gtid_executed;

-- 从库
SELECT @@GLOBAL.gtid_executed;

-- 等待从库执行到指定 GTID（用于读一致性）
SELECT WAIT_FOR_EXECUTED_GTID_SET('3e11fa47-71ca-11e1-9e33-c80aa9429562:1-1000', 2);
```

## 4. 复制模式：异步、半同步与组复制

### 4.1 异步复制

主库提交后立即返回，不等待从库。性能最好，但主库故障时可能丢失尚未传送到从库的事务。

### 4.2 半同步复制

主库等待至少一个从库确认收到 binlog（或回放完成）后再向客户端返回。MySQL 8 常见参数：

```ini
[mysqld]
plugin_load_add = rpl_semi_sync_source.so
rpl_semi_sync_source_enabled = ON
rpl_semi_sync_source_timeout = 1000
rpl_semi_sync_source_wait_point = AFTER_SYNC
```

```sql
-- 从库安装并启用插件（插件名随版本变化）
INSTALL PLUGIN rpl_semi_sync_replica SONAME 'rpl_semi_sync_replica.so';
SET GLOBAL rpl_semi_sync_replica_enabled = ON;

SHOW STATUS LIKE 'Rpl_semi_sync%';
```

要点：

- `AFTER_SYNC` 表示在引擎提交前等待 ACK，客户端看到提交时，至少一个从库已收到日志；`AFTER_COMMIT` 是旧行为，主库崩溃后可能出现在从库未收到但主库已提交的窗口；
- 半同步通常只要求“一个”从库确认。如果接管者恰好是没收到事务的那个副本，仍可能丢数据；
- 超时后会退化为异步，恢复后自动回到半同步（取决于版本与配置），需要监控退化事件；
- 真正“零丢失自动切换”通常需要组复制、InnoDB Cluster 或基于共识的托管服务。

### 4.3 组复制 / InnoDB Cluster

组复制基于 Paxos 类协议做多数派确认，支持自动选主和成员管理。它解决的是“复制 + 一致性 + 部分自动化”，但仍有网络分区、脑裂防护和性能权衡。生产使用建议配合 MySQL Router、清晰的路由策略和定期切换演练。

## 5. 延迟的常见原因

1. **大事务**：一次更新百万行，binlog 事件巨大，回放耗时且无法并行；
2. **DDL**：部分 DDL 在从库串行执行，且可能锁表；
3. **无主键/无索引更新**：从库回放时要扫描大量行；
4. **单线程回放**：写入并发高但事务依赖强，并行度上不去；
5. **从库资源不足**：磁盘 IOPS、CPU、Buffer Pool 小于主库；
6. **网络带宽/抖动**：日志传输慢；
7. **从库承担大量只读查询**：与回放线程争抢资源；
8. **复制过滤规则**：过滤后数据不一致，后续语句可能报错。

排查顺序：先看 `SHOW REPLICA STATUS` 的 IO/SQL 线程与错误，再看 `Relay_Log_Space` 是否持续增长，结合主库 binlog 生成速率、从库磁盘 IO 和慢日志判断。

```sql
-- MySQL 8 复制性能视图
SELECT * FROM performance_schema.replication_applier_status_by_worker\G
SELECT * FROM performance_schema.replication_connection_status\G
```

## 6. 高可用切换的关键问题

### 6.1 先明确 RPO/RTO

- **RPO**：能接受丢多少数据？异步复制可能是秒级甚至更多；半同步最多一个 ACK 副本的差距；组复制可做到多数派内不丢。
- **RTO**：故障后多久恢复？取决于检测、选主、DNS/VIP 切换、连接池重连和应用启动。

没有 RPO/RTO 的“高可用方案”无法验收。

### 6.2 切换不是“把从库 read_only 关掉”

一次安全切换至少包含：

1. **确认候选副本数据最新**：比较 GTID 集合，确保候选者包含所有已提交事务；
2. **停止写入或冻结主库**：`SET GLOBAL super_read_only=ON`，等待在途事务结束；
3. **等待所有可接管副本追平**；
4. **选主并提升**：停止候选副本复制，解除只读；
5. **重新指向其他副本**：使用 GTID 自动定位；
6. **切换流量**：VIP、DNS、ProxySQL、MySQL Router 或服务发现；
7. **旧主处理**：禁止直接以旧身份加入，先确认无 errant transaction，必要时用 Clone 重建；
8. **验证**：读写、复制、延迟、GTID 一致性、应用健康检查。

### 6.3 防止脑裂

必须确保旧主不再接受写入。常见手段：

- STONITH/电源 fencing；
- 交换机/安全组隔离；
- 云平台实例终止；
- 仲裁服务与 lease；
- 应用侧只写唯一入口。

仅靠“检测到主库挂了就提升从库”非常危险：网络分区时，旧主可能仍存活并接受写入，形成双主。

### 6.4 自动化工具

- **Orchestrator**：拓扑发现、故障检测、切换与修复；
- **MySQL Router + InnoDB Cluster**：组复制拓扑中的路由与故障转移；
- **ProxySQL**：读写分离、后端健康检查与查询路由；
- **MHA**：较早期的方案，新项目需评估维护状态；
- 云托管数据库：通常内置多可用区切换，但仍需理解其 RPO/RTO 和连接串行为。

工具不是银弹。必须演练：主库宕机、网络分区、复制中断、候选副本落后、切换过程中应用重连。

## 7. 读写分离与一致性

读写分离后，最常见的用户可见问题是“刚写入就查不到”。解决方案：

1. **写后读走主库**：对一致性敏感的请求强制主库；
2. **会话粘性**：同一会话短时间内固定主库；
3. **GTID 等待**：在从库执行 `WAIT_FOR_EXECUTED_GTID_SET`，等待到指定事务；
4. **业务补偿**：前端短暂重试或显示“处理中”；
5. **避免长事务**：长事务会推迟从库可见时间。

还要考虑：

- 从库延迟告警阈值应结合业务 SLA；
- 只读实例的负载与回放线程争抢；
- 故障切换后连接池中的旧连接；
- 事务内混用读写连接会破坏一致性。

## 8. 延迟副本与误操作恢复

保留一个延迟副本（如延迟 1 小时）对“误删数据”非常有价值：

```sql
CHANGE REPLICATION SOURCE TO
  SOURCE_DELAY = 3600;
```

注意：

- 延迟副本的 `Seconds_Behind_Source` 会显示约 3600，不要误判为故障；
- 它不能替代备份，因为主库若发生物理损坏，延迟副本也可能受影响；
- 误删后应尽快隔离写入，在延迟副本上确认时间点，再导出数据或做 PITR。

## 9. 监控与演练清单

- [ ] 复制线程状态、GTID 差距、延迟分位数；
- [ ] 半同步退化为异步的次数与持续时间；
- [ ] binlog 生成速率、磁盘空间、保留时长；
- [ ] 从库 IOPS、CPU、Buffer Pool 命中率；
- [ ] 主从数据一致性校验（pt-table-checksum 等）；
- [ ] 每季度至少一次切换演练，记录实际 RTO；
- [ ] 切换后旧主隔离与重建流程；
- [ ] 应用连接池的重连、超时与只读降级策略。

## 10. 小结

复制是数据冗余的基础，高可用是“检测 + 决策 + 隔离 + 切换 + 验证”的系统工程。选型时先写清 RPO/RTO，再决定异步、半同步还是组复制；上线前用真实故障演练验证，而不是只看架构图。
