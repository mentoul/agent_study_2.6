# MySQL 备份、恢复与误删救援

> 一句话结论：**没有验证过恢复的备份，不算备份。** 备份方案的核心指标不是“备份成功”，而是“在多长时间内、恢复到哪个时间点、数据是否可用”。

## 1. 先定义 RPO 与 RTO

- **RPO（Recovery Point Objective）**：最多能接受丢失多长时间的数据。例如 RPO = 5 分钟，意味着必须有连续的 binlog 归档或更高频备份。
- **RTO（Recovery Time Objective）**：从故障发生到业务恢复可用的最长时间。它决定了你是直接重建实例、原地恢复，还是切换到备用环境。

一个常见的分层策略：

| 层次 | 内容 | 作用 |
| --- | --- | --- |
| 全量备份 | 每周/每日一次物理或逻辑备份 | 提供恢复基线 |
| 增量备份 | 每日/每小时 | 缩短恢复时需要回放的日志量 |
| binlog 归档 | 持续 | 支持任意时间点恢复（PITR） |
| 延迟副本 | 延迟 1 小时等 | 快速绕过误操作，但不等同备份 |
| 恢复演练 | 每月/季度 | 验证备份可用性与 RTO |

同时遵循 **3-2-1 原则**：至少 3 份副本、2 种介质、1 份异地；并对备份加密、限制访问、防止被勒索软件或误删一并清除。

## 2. 逻辑备份：mysqldump

适合中小数据量、跨版本迁移、单表恢复。优点是纯文本、可读、可选择性恢复；缺点是备份和恢复慢，对大库不友好。

```bash
mysqldump \
  --host=127.0.0.1 \
  --user=backup \
  --password \
  --single-transaction \
  --quick \
  --routines \
  --triggers \
  --events \
  --source-data=2 \
  --set-gtid-purged=OFF \
  --databases app \
  > /backup/app-$(date +%F-%H%M).sql
```

参数说明：

- `--single-transaction`：在 REPEATABLE READ 下开启一致性快照，适用于 InnoDB；备份期间应避免 DDL，否则可能破坏一致性；
- `--quick`：逐行读取，避免把大结果集全部放进内存；
- `--routines --triggers --events`：包含存储过程、触发器、事件；
- `--source-data=2`：以注释形式记录 binlog 坐标（旧版本为 `--master-data`），便于 PITR；
- `--set-gtid-purged=OFF`：导入到独立实例时避免 GTID 冲突；若用于搭建复制，应改为 `ON` 或 `AUTO` 并理解其影响；
- `--databases app`：让备份文件包含 `CREATE DATABASE`/`USE`，恢复时不必手工建库。

如果备份账号没有 `PROCESS` 权限，可能还需要 `--no-tablespaces`。对 MyISAM 等非事务表，`--single-transaction` 无法保证一致性，需要短暂的全局读锁，务必评估锁影响。

恢复：

```bash
mysql --host=127.0.0.1 --user=root --password < /backup/app-2026-11-11-0200.sql
```

大文件恢复时可观察进度：

```bash
pv /backup/app.sql | mysql -uroot -p app
```

## 3. 物理备份：XtraBackup

物理备份直接复制数据文件，适合大库，恢复速度快。以 Percona XtraBackup 8.0 为例：

```bash
# 全量备份
xtrabackup --backup \
  --target-dir=/backup/full-20261111 \
  --user=backup --password='***'

# 准备（应用 redo，使数据文件一致）
xtrabackup --prepare --target-dir=/backup/full-20261111

# 恢复到空数据目录
systemctl stop mysqld
xtrabackup --copy-back \
  --target-dir=/backup/full-20261111 \
  --datadir=/var/lib/mysql
chown -R mysql:mysql /var/lib/mysql
systemctl start mysqld
```

增量备份示例：

```bash
# 基于全量做增量
xtrabackup --backup \
  --target-dir=/backup/inc-20261112 \
  --incremental-basedir=/backup/full-20261111 \
  --user=backup --password='***'

# 准备：先处理全量，再应用增量
xtrabackup --prepare --apply-log-only --target-dir=/backup/full-20261111

# 应用增量；如果还有后续增量，这一条要带 --apply-log-only
xtrabackup --prepare --target-dir=/backup/full-20261111 \
  --incremental-dir=/backup/inc-20261112

# 结论：只有最后一个增量不带 --apply-log-only，
# 让 InnoDB 完成回滚/恢复；不要在最后再对 base 单独 prepare 一次。
```

注意：

- XtraBackup 版本必须与 MySQL 版本兼容，8.4 与 8.0 的工具链不同；
- 恢复前确保目标 `datadir` 为空，避免残留文件；
- 备份账号需要 `BACKUP_ADMIN`、`RELOAD`、`PROCESS`、`REPLICATION CLIENT` 等权限；
- 备份期间监控磁盘空间、redo 生成速率和备份时长；
- 物理备份不能直接跨大版本降级恢复。

## 4. binlog 与 PITR

全量备份只能恢复到备份时刻。要恢复到“误删前一秒”，需要：

```text
全量备份（T0） + binlog（T0 → 目标时间点）
```

### 4.1 找到误操作位置

先在 binlog 中定位 `DROP TABLE` / `DELETE` 的时间与位置：

```bash
mysqlbinlog --base64-output=DECODE-ROWS -vv \
  --start-datetime='2026-11-11 09:50:00' \
  --stop-datetime='2026-11-11 10:10:00' \
  /backup/binlog/mysql-bin.000123 \
  | less
```

关注 `# at <position>`、`SET TIMESTAMP=`、`GTID_NEXT=` 以及实际 SQL。**不要在生产库直接试回放**，先恢复到隔离实例。

### 4.2 恢复到误操作前

```bash
# 1. 恢复全量备份到临时实例
mysql -uroot -p < /backup/app-full.sql

# 2. 回放 binlog 到误操作之前
mysqlbinlog \
  --start-position=123456 \
  --stop-position=789012 \
  /backup/binlog/mysql-bin.000123 \
  | mysql -uroot -p

# 或按时间回放
mysqlbinlog \
  --start-datetime='2026-11-11 02:00:00' \
  --stop-datetime='2026-11-11 10:00:00' \
  /backup/binlog/mysql-bin.000123 \
  | mysql -uroot -p
```

使用 GTID 时，可用 `--include-gtids` / `--exclude-gtids` 精确控制，但要注意不要重复回放已执行事务。回放前记录目标实例的 `gtid_executed`，并确认 binlog 未被 purge。

### 4.3 只恢复一张表

如果误删的是一张表，而其他表仍在写入，直接全库 PITR 会丢失后续数据。更稳妥的流程：

1. 立即停止或限制对该表的写入，保留现场；
2. 在隔离实例恢复到误删前的时间点；
3. 从临时实例导出该表（`mysqldump app orders > orders.sql`）；
4. 在生产库执行 `RENAME TABLE` 备份当前表，再导入恢复表；
5. 校验行数、主键范围、关键业务字段；
6. 确认无误后再清理临时表。

### 4.4 误删后的第一反应

- **不要急着重启或重建主库**；
- 立即停止相关写入，避免 binlog 继续增长覆盖；
- 确认备份、binlog 归档是否完整；
- 记录故障时间、操作账号、SQL、影响范围；
- 在隔离环境验证恢复步骤；
- 评估是“单表恢复”还是“全库 PITR”，优先减少数据丢失范围。

## 5. 恢复演练：把备份变成能力

建议每月至少做一次抽样恢复，每季度做一次完整演练：

- [ ] 从对象存储/异地拉取备份，验证校验和与可解密；
- [ ] 在隔离环境完成全量恢复 + binlog 回放；
- [ ] 记录实际恢复耗时，与 RTO 对比；
- [ ] 校验表数量、行数、关键业务查询、外键/约束；
- [ ] 验证复制关系与 GTID 一致性；
- [ ] 检查应用连接、账号权限、字符集、时区；
- [ ] 输出演练报告，修正 runbook。

校验示例：

```sql
SELECT COUNT(*) FROM app.orders;
SELECT MIN(id), MAX(id) FROM app.orders;
CHECKSUM TABLE app.orders;
```

`CHECKSUM TABLE` 对大表开销较大，生产使用需谨慎；跨版本/跨引擎校验也可能不一致。更完整的一致性校验可考虑 `pt-table-checksum` 等工具，并理解其锁与复制影响。

## 6. 备份安全与运维

- **加密**：备份文件静态加密，密钥与备份分离管理；
- **访问控制**：备份账号最小权限，下载与恢复操作审计；
- **不可变存储**：对象存储开启版本控制/对象锁，防止误删和勒索；
- **保留策略**：按合规与业务需求设置日/周/月保留，定期清理；
- **监控**：备份任务失败、耗时异常、文件大小骤变、binlog 归档延迟都要告警；
- **容量**：恢复时需要额外的磁盘空间，提前规划；
- **版本兼容**：升级 MySQL 前确认备份工具支持新版本，并保留旧版本恢复路径。

## 7. 小结

备份不是“定时跑一个脚本”，而是一套以 RPO/RTO 为目标、以恢复演练为验收的体系。逻辑备份灵活、物理备份快、binlog 负责时间点，三者组合才能覆盖误删、介质损坏、实例故障等不同场景。真正发生事故时，最值钱的是**经过演练的恢复步骤**，而不是备份文件本身。
